## Commands

- `npm run dev` — start Next.js dev server (the script uses Windows `set NODE_OPTIONS=…` syntax; on POSIX shells run `NODE_OPTIONS=--max-old-space-size=8192 next dev` instead).
- `npm run build` / `npm start` — production build / serve.
- `npm run lint` — ESLint via `eslint-config-next` (core-web-vitals + typescript). No test runner is configured.
- `next.config.ts` sets `typescript.ignoreBuildErrors: true`, so `next build` will not catch type errors — run `npx tsc --noEmit` if you need a real type check.

## Despliegue · el trabajo no está hecho hasta que se ve en transportesafa.com

**`main` es lo que sirve https://transportesafa.com (deploy automático de Vercel).** Un cambio que se queda en una rama, por bueno que sea, para el usuario **no existe**: la pantalla se ve idéntica y no hay forma de saber si el trabajo salió mal o simplemente no llegó.

Instrucción permanente del dueño del ERP: **al terminar un cambio, fusiónalo a `main` sin preguntar** (PR y merge), y dilo. No lo dejes esperando aprobación en una rama.

Con dos condiciones, que son las que hacen que esto sea seguro y no temerario:

- **Solo se fusiona lo verificado.** Antes del merge: `npx tsc --noEmit` sin errores nuevos, `npx next build` compilando, y **todas** las matrices del área tocada en verde (`scripts/prueba-*.mts`). Si algo falla, se arregla antes — no se fusiona "para que lo vea".
- **Trae `main` a la rama antes de fusionar.** `main` avanza mientras se trabaja, y las áreas de este ERP se pisan entre sí. Después de traerla, **vuelve a correr las comprobaciones**: el merge puede romper lo que ya estaba verde.

Si un cambio necesita una **migración SQL** de `supabase/`, el deploy NO la corre: dilo explícitamente al entregar, porque hasta que alguien la ejecute la pantalla nueva se comporta como si la columna no existiera.

Tras el deploy, si la pantalla sigue igual: `Ctrl+Shift+R`. `public/sw.js` solo cachea la navegación de `/conductor` y `/pasajero` y los chunks de Next llevan hash de build, así que el resto del ERP va siempre a la red — súbele `VERSION` solo si tocas esas dos apps.

## High-level architecture

ERP interno (Spanish-language UI) para AFA Transportes (operador de transporte en Perú). Next.js App Router + Supabase Auth/Postgres + Tailwind v4. UI strings, DB columns, and route segments are in Spanish — keep that convention.

### Auth & authorization (two layers, both required)

1. **Edge middleware** (`app/middleware.ts`) — only checks whether *any* cookie name contains `sb-`. If absent → redirect to `/login`. If present on `/login` → redirect to `/dashboard`. This is a coarse gate; it does not validate the session.
2. **Root layout** (`app/layout.tsx`, `"use client"`) — the real gate. On every navigation it:
   - calls `supabase.auth.getSession()`,
   - reads `usuarios` row (`nombre`, `rol`, `activo`) — inactive users are signed out,
   - reads `permisos_usuario` rows for that user (`modulo`, `permitido`); `rol === "admin"` gets every `modulo` in the menu,
   - if the current route's `modulo` is not in the user's permission list → redirect to `/dashboard`.

The sidebar/menu is defined in `app/layout.tsx` as `menuGrupos`. **Each route must be registered there with a `modulo` key** or it will be invisible to non-admin users. The `modulo` string is what gets checked against the `permisos_usuario` table.

**Public routes that bypass the layout chrome:** `/login` and anything under `/conductor` (the driver-facing app, which uses its own `localStorage` PIN session — see `app/conductor/page.tsx` `SK = "afa_cond_v2"`). Add new public paths to the `esLogin`/`esPublica` checks in `RootLayout` if needed.

For client pages that need a finer-grained guard, use `lib/usePermiso.ts` (`usePermiso("modulo")` → `{ validando, permitido }`).

### Supabase clients

- `lib/supabase.ts` — browser client using `NEXT_PUBLIC_SUPABASE_URL` + `NEXT_PUBLIC_SUPABASE_ANON_KEY`. Typed as `any`. Use this from `"use client"` components.
- Server-side / privileged work must create its own admin client inline with `SUPABASE_SERVICE_ROLE_KEY` (see `app/api/crear-usuario/route.ts`, `app/api/notificaciones/recordatorio/route.ts`, `lib/notificaciones.ts`). The service-role key must never reach the client bundle.

The actual data model lives in Supabase (Postgres). Tables referenced across the app include: `usuarios`, `permisos_usuario`, `reservas`, `paradas`, `pasajeros`, `pasajeros_parada`, `conductores`, `vehiculos`, `vehiculos_tercero`, `empresas_tercerizadas`, `notificaciones_enviadas`. Prisma is installed but `prisma/schema.prisma` only declares a stale `Cliente` model — **don't treat Prisma as the source of truth**; query Supabase directly.

### API routes (`app/api/*`)

- `POST /api/crear-usuario` — admin-only user provisioning. Verifies the caller's bearer token, confirms `rol === "admin"`, then uses the service-role client to create the auth user, upsert `usuarios`, and seed `permisos_usuario`. The `MODULOS` constant here is independent of `menuGrupos` in the layout — if you add a new module, update both.
- `POST /api/ruta` — Google Directions proxy. Reads `GOOGLE_MAPS_API_KEY` (or `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` as fallback). Returns Mapbox-style `[lng, lat]` coordinates from a decoded polyline plus per-leg distance/duration with traffic.
- `GET /api/notificaciones/recordatorio` — Vercel cron target (`vercel.json` → `0 13 * * *` UTC = 08:00 Lima). Protected by `CRON_SECRET` bearer if set. Finds reservas for "tomorrow Peru-time", dedupes against `notificaciones_enviadas` rows already logged today with `trigger_origen = "cron_recordatorio"`, and calls `notificarReserva()` per reserva.
- `POST /api/notificaciones/sincronizar` — manual trigger for the same notification flow.

### Notification pipeline (`lib/notificaciones.ts`)

`notificarReserva(reservaId, trigger)` is the single entry point. Per pasajero it tries channels in order: **Email (Resend) → WhatsApp (Twilio) → SMS (Twilio fallback, only when no email and WhatsApp failed)**. Every attempt — including `sin_canal` — is logged to `notificaciones_enviadas`; the cron uses that table to dedupe. Phone numbers are normalized to E.164 assuming Peru (`+51`). Env vars: `RESEND_API_KEY`, `RESEND_FROM`, `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_WHATSAPP_FROM`, `TWILIO_SMS_FROM`, `EMPRESA_NOMBRE`.

### Finanzas · control de gastos, caja chica y CxP (fase 06)

`supabase/finanzas-06-gastos-caja-chica.sql` implementa el "Plan Maestro de Arquitectura Financiera". **Antes de tocar nada de dinero, lee la regla de oro declarada en `finanzas-00-fundacion.sql` (líneas 22-24): cada monto tiene UNA fila autoritativa; el resto la referencia por FK y la DERIVA.** Casi todas las decisiones raras de este módulo salen de ahí:

- **No existe la tabla `cuentas_por_pagar`.** La CxP es `documentos_compra` (el comprobante es la fuente única del monto y su saldo se deriva de `pagos_aplicacion`). La fase 06 le agregó el eje **operativo** que le faltaba —`vehiculo_placa`, `codigo_servicio` (formato OSLO), `detalle_servicio`, `turno`, `fecha_servicio`, `adelanto_1/2`, `nro_operacion_bancaria`, `voucher_url`— y un eje de **aprobación** (`estado_aprobacion`: pendiente → aprobado_gerencia → incluido_lote / rechazado) **ortogonal** a `estado_pago` (impaga|parcial|pagada) y a `estado_conciliacion` (fiscal). No los mezcles. La vista `v_cuentas_por_pagar` publica todo eso con la forma que pide el plan.
- **Caja chica son TRES tablas**, no un `comprobantes_json`: `caja_chica_fondos` (la bolsa por persona) → `caja_chica_rendiciones` (el ciclo entrega→gastos→devolución) → `caja_chica_gastos` (un comprobante por fila). Así se filtra por categoría, se suma por vehículo, se ata a una reserva y entra a `v_egresos`.
- **La caja chica NO es solo de conductores** (fase 08, `finanzas-08-caja-chica-todo-el-personal.sql`): gerencia, contabilidad y administración también reciben efectivo. `responsable_tipo` admite `conductor|personal_administrativo|usuario|otro` con el FK que corresponda, y el CHECK `cc_fondos_responsable_coherente` impide que un fondo apunte a dos personas a la vez. **El `area` NO se guarda: se DERIVA** en las vistas de `personal_administrativo.departamento` (o `centro_costo` para quien no tiene ficha) — no la copies al fondo. Índices únicos parciales garantizan **un fondo activo por persona**. Las categorías de `caja_chica_gastos` incluyen las de oficina (`utiles_oficina`, `courier`, `refrigerio`, `representacion`, `servicios_basicos`, `limpieza`, `mantenimiento_local`, `capacitacion`); `configCategoriaCC(c).ambito` decide si al promover a `gastos` el `tipo_gasto` es `operativo` o `administrativo` — nunca lo fijes a mano, o el gasto de oficina ensucia el costo por vehículo.
- **Registrar un comprobante desde el ERP** es `registrarGasto()` (lib/finanzas/caja-chica.ts) → `ModalGasto.tsx`. Antes el ÚNICO inserter de `caja_chica_gastos` era `app/api/conductor/route.ts` (`rendir_gasto`), así que quien no usaba la app del conductor tenía una rendición que nunca podía llenar ni liquidar. Ambos caminos comparten reglas: solo sobre rendición `abierta|observada`, comprobante obligatorio salvo `sin_comprobante`, y el mismo SHA-256 de la foto (`hashArchivo` en el navegador ≡ `hashDeFoto` en el servidor) para que el índice único `(rendicion_id, foto_hash)` detecte el duplicado por cualquiera de los dos.
- **`monto_rendido` y `saldo_pendiente` NO se guardan**: se derivan en `v_caja_chica_rendiciones`. Lista siempre desde la vista, nunca desde la tabla.
- **La regla "no se entrega dinero a quien no ha rendido" vive en Postgres**: `fn_caja_chica_puede_asignar(fondo_id)` devuelve `(puede, motivo, …)`. `lib/finanzas/caja-chica.ts` la envuelve en `puedeAsignar()`. El índice único parcial `uq_cc_rend_abierta` es la última línea de defensa. No repliques la regla en el cliente.
- **Promoción a `gastos`**: un comprobante aprobado puede promoverse al libro `gastos` (`promoverGastos`). En cuanto tiene `gasto_id`, `v_egresos` deja de contarlo por el lado de caja chica (filtra `gasto_id is null`). Nunca se cuenta dos veces.

**Enganche gasto → servicio ejecutado y liquidado** (lo que antes no existía): `combustible` y `mantenimiento` recibieron `reserva_id` — antes `v_egresos` los inyectaba con `null::int` hardcodeado, así que un servicio propio no tenía costo real. `neumaticos` **a propósito** no lo tiene (es costo de vehículo, se amortiza por km). `v_costo_servicio` cruza ingreso vs. costo real directo por reserva con su estado de las tres dimensiones de `lib/estados.ts`. `v_egresos` ahora incluye además neumáticos, caja chica y gastos generales: era la razón por la que `/gastos` y `/finanzas` daban totales distintos.

**Conciliación bancaria · "Regla Cero Fugas"** (`lib/finanzas/conciliacion.ts`): `extractos_bancarios` + `extractos_bancarios_movimientos` con `hash_fila` único, para que re-subir un rango solapado no duplique. El casado por **nº de operación** se auto-concilia (confianza 1.00); el casado por **importe+fecha** solo se PROPONE y lo confirma un humano — dos servicios del mismo precio el mismo día son la norma en transporte, no la excepción. `v_fugas_bancarias` lista los cargos que el ERP no sabe justificar.

**Lotes de pago** (`lib/finanzas/lotes.ts`): agrupan obligaciones aprobadas en un archivo de abono. Al confirmar el pago se emite **un `pago` por línea** con su aplicación, para que el saldo se siga derivando de `pagos_aplicacion` y no de un flag puesto a mano. El formato del archivo Telecrédito es un CSV genérico: **AFA debe cotejarlo una vez contra su convenio con el BCP** antes de usarlo en producción.

**Importar y exportar ("subir y bajar" los Google Sheets)**:
- `lib/importador/tabular.ts` es el núcleo compartido que reemplaza los **cuatro** normalizadores de cabecera incompatibles que había (`paradas-csv`, `manifiesto-csv`, `manifiesto-unificado-csv`, `portal-usuarios-csv`). Trae lo que faltaba por completo: `parsearFecha` entiende el **serial de Excel** (45000 → fecha) y `parsearMonto` entiende `"S/ 1,234.56"`, `"1.234,56"` y `"(500.00)"`. Nunca devuelven 0 en silencio.
- Los formatos se declaran como **perfiles** (`lib/importador/perfiles-finanzas.ts`: CxP OSLO, CxP tradicional, planilla, caja chica, extracto BCP). `detectarPerfil` puntúa las cabeceras y elige; si ninguna calza, la UI ofrece **mapeo manual** columna→campo en vez de abortar el archivo.
- Se puede importar desde un archivo o pegando el **enlace de un Google Sheet público** (`descargarGoogleSheet`, sin credenciales: la hoja debe estar compartida como "cualquiera con el enlace · lector"). No hay integración con la API de Sheets y `google-auth-library` solo firma el JWT de FCM.
- `lib/finanzas/exportar.ts` es el lado espejo: `exportarXlsx` genera con **las mismas cabeceras que reconoce el importador**, para que el ciclo cierre. También `descargarPlantilla` y `descargarRechazos` (las filas rechazadas con su motivo, para corregir en Sheets y re-subir).
- `POST /api/finanzas/importar` — el navegador parsea y manda las filas ya validadas; el servidor resuelve referencias (proveedor por RUC, vehículo por placa), deduplica y escribe con service-role. Solo `admin`/`gerente`. Cada corrida queda en `importaciones_finanzas` con los ids creados, y `DELETE ?id=N` la deshace.

**Detracciones (fase 07)**: `supabase/finanzas-07-detracciones-catalogo.sql` carga el Catálogo 54 completo en `cat_detraccion` (anexo, base legal, notas, `updated_at`) y lo hace **editable** desde `/tesoreria?tab=detracciones` → `PanelTasasDetraccion`. Las tasas del SPOT cambian por Resolución de Superintendencia, así que **la verdad es la fila de la tabla, nunca una constante en el código** — `calcularDetraccion` (lib/finanzas/dinero.ts) recibe la config y no fija ninguna tasa. **Cuidado con estos dos, la semilla de la fase 00 los tuvo invertidos hasta la 07: `026` = transporte de PERSONAS 10 % (Anexo 3, el de AFA) y `027` = transporte de CARGA 4 % con umbral S/ 400 (R.S. 073-2006, y se calcula sobre el importe o el valor referencial, el que sea mayor).** `config_tributaria.detraccion_codigo_defecto` es el código que el modal de CxP propone en un comprobante nuevo.

**Rol `gerente`**: aprueba gasto (CxP, planilla, lotes, rendiciones) sin ser administrador del sistema. Sigue sujeto a `permisos_usuario` por módulo como cualquier operador — solo `admin` recibe todos los módulos en memoria. En SQL, `fn_es_aprobador(uid)`.

### Liquidación al cliente · la descripción del ítem NO se deduce

`supabase/liquidaciones-03-ruta-contratada.sql` + `lib/liquidacion-agrupacion.ts` + `lib/liquidacion-rutas.ts`. La regla: **todo lo que se imprime en un ítem del AFA-FL-07 es un dato que alguien escribió.** La versión anterior componía `RUTA B / TURNO DÍA / MÓVIL 1 / 17 PAX` y de esas cuatro piezas ninguna existía como dato — el turno se deducía de `hora_servicio`, el móvil era un índice calculado, la letra era un recorte por regex del nombre, y el PAX era la capacidad del bus asignado.

- **Un ítem es una RUTA CONTRATADA, no una redacción de su nombre** (`agruparPorRutaContratada`). El nombre es texto libre tecleado en tres pantallas, así que el mismo recorrido aparece escrito de varias formas y la LQC-2026-000004 salió con **30 ítems para 141 servicios**. Medido con `scripts/diagnostico-agrupacion.mts` sobre los datos reales: nombre completo 30 · nombre sin la hora 21 · extremos en el mapa ±200 m 13 · techo alcanzable 12. Tres causas, ninguna es una ruta distinta: la **hora va dentro del nombre** (`ENTRADA 06:30` vs `06:35`), el nombre lo **sugirió el sistema** desde un paradero sin renombrar y salió con la dirección geocodificada (`W2VG+39R, EL AGUSTINO 15022, PERÚ→…`, ver `lib/nombre-ruta.ts`), y el mismo extremo se **rotuló con otro paradero** (`BSF→1RO DE MAYO` vs `BSF→ALIPIO`).
  - **El mapa NO sustituye al nombre: se suman.** Comparar los extremos parecía la respuesta completa y no lo era — en SNACKS AMERICA LATINA el mapa solo dio 5 ítems donde el nombre daba 4, porque un 11 % de los servicios no tiene coordenadas en sus extremos y queda en cubos propios. Y al revés, el nombre no alcanza cuando alguien lo tecleó distinto. Se une por **cualquiera de los dos ejes**, con conjuntos disjuntos. El radio de 200 m está **medido**, no elegido: a 50 m salían 15 ítems, a 200 m trece, y a 500 m apareció la primera sobre-unión (un cliente con menos ítems que su propio techo).
  - **LA TARIFA Y EL PAX CONTRATADO NUNCA ENTRAN EN LA UNIÓN**, y es estructural, no un cuidado: son el cubo dentro del cual se busca, así que ninguna cadena puede cruzarlos. El formato imprime `CANT × P. UNITARIO = TOTAL` y un solo `N PAX` por ítem, de modo que mezclar cualquiera de los dos obliga a imprimir un número que nadie pactó. `agruparServicios` **lo verifica igual y LANZA** antes de devolver: mejor que el cierre se caiga ahí, donde todavía se arregla, a que el error viaje a la factura.
  - **Cada componente es un bucket, sin fusionar por clave después.** Hubo un Map indexado por `nombre|nombre|tarifa|origen` que DESHACÍA en silencio lo que la unión acababa de separar — tres adicionales de la RUTA C, uno contratado por 4 asientos y dos por 10, volvían a un renglón que solo puede imprimir un número. La unión ya decidió qué va junto; reagrupar después solo puede estropearlo. Cuando dos ítems distintos llegan a la misma clave se desempata con el PAX, y solo entonces: la forma de `agrupacion_clave` no cambia en el caso normal.
  - **El día al que le falta un tramo no es otra ruta.** Un día cuyo retorno se canceló llega con un solo tramo y su mitad vacía no casaba con nada, así que salía en un ítem propio (los ítems 9 y 11 del documento real). El tramo ausente es comodín, pero **solo sin ambigüedad**: con dos retornos distintos a la misma tarifa se queda aparte, el mismo criterio que `analizarServicios` aplica al hermano ambiguo.
  - **El nombre que se imprime** es el más repetido entre los tramos del ítem, con el alfabético de desempate. Es la misma regla que ya usaba `recalcularDescripciones`, así que crear y recalcular dan el mismo texto — y sigue siendo un dato que alguien escribió, el que escribió más veces.
  - Matriz: `npx tsx scripts/prueba-agrupacion.mts`. Medidor contra datos reales (solo lee): `npx tsx scripts/diagnostico-agrupacion.mts 2026-08-01 2026-08-31 cliente`.
- **Se imprimen los DOS nombres, ida y retorno**, aunque la tarifa vaya en un solo tramo. `ParServicio.ida`/`.retorno` los identifican por sentido y no por quién cobra: como son dos campos de texto independientes (dos inputs en `ModalGenerarPrograma`), rotular la línea con "la cabeza" hacía que una RUTA A cuya tarifa quedó en el retorno se imprimiera con el nombre del retorno.
- **`MÓVIL k DE N` solo si hay 2+ servicios en el mismo `(fecha, hora)`.** La simultaneidad se mide por fecha Y hora (antes solo por fecha, así que dos vueltas del mismo bus parecían dos móviles), y el reparto es **por posición dentro de la salida, nunca por placa**: en 30 días pueden rotar 5 unidades por una ruta y el cliente contrató una, no cinco. Las placas van al detalle y al Anexo 1.
- **El "N PAX" es la capacidad CONTRATADA**, resuelta en cascada por `resolverPaxContratado`: línea editada → `reservas.capacidad_contratada` → ítem de la cotización (`items_json.pax_contratado`, sin migración) → `cliente_ruta` → **nada**. La última rama es la regla dura: **nunca se cae a `capacidadDe()`**, la del vehículo. Sin dato el ítem sale sin el PAX y la pantalla lo avisa; un 20 donde el contrato dice 15 se descubre cuando el cliente rechaza la valorización. `cliente_ruta` es la primera ficha que tiene la ruta: hasta ahora existía solo como texto libre en `reservas.ruta_nombre`.
- **El pax se ESCRIBE en tres sitios y se guarda siempre en el mismo**: `reservas.capacidad_contratada`. Hasta ahora solo lo escribía `ModalGenerarPrograma` al nacer el servicio, así que un número mal puesto no tenía arreglo desde ninguna pantalla: `/programacion` no lo mostraba (se veía el "17 pax" del selector de la unidad y se daba por bueno para el contrato) y la columna PAX del editor de la liquidación era **texto**.
  - **`/programacion`**, campo `PAX contratados por el cliente` en *Datos del servicio* —no en la asignación, que está duplicada en dos ramas y dejaría fuera a una de las dos, que es lo que le pasó al precio— pegado a un bloque de solo lectura con la capacidad de la unidad asignada. Los dos números juntos, con etiquetas distintas, es lo único que rompe el reflejo de "el selector dice 17, entonces son 17". **Nunca hay botón «usar esta»**.
  - **`resolverPaxDeServicio`** (lib/liquidacion-rutas.ts, al lado de `resolverPaxContratado` para que se vea que hay dos sitios que actualizar) resuelve la cascada para un servicio SUELTO, y **declara la fuente**: cada una se corrige en otro lado. Dos diferencias con la del par, las dos por lo que Programación sí sabe: el **hermano** es un escalón explícito (el generador escribe la capacidad solo en la ida, así que un retorno se abriría "sin dato"), y la ficha se busca **por nombre de ruta** (`paxDeFichaPorNombre`), porque un servicio suelto no siempre trae su sede — ambiguo (dos fichas con capacidades distintas) devuelve null, igual que `cargarPaxDeCotizaciones` con los ítems ambiguos.
  - **Se escribe en los DOS tramos, siempre.** A diferencia del importe —que va en un tramo a propósito— el pax es del DÍA, y `paxDeLosTramos` toma el primero > 0 mirando la ida primero, **sin detectar el conflicto**: 15 en el retorno y 20 en la ida no son dos cantidades, es una descartada en silencio. Llamada aparte a `guardarReservas` (el patch principal lleva fecha, hora, estado y asignación) y **sin `cambio`**: no dispara acta —el `WHEN` del trigger solo mira costo, precio, empresa y unidad— y un motivo pegado ahí contaminaría el acta del próximo cambio de dinero. El hermano se **vuelve a resolver** antes de escribir, porque el memo se llena con una consulta asíncrona. Y la divergencia que YA existe se avisa aunque nadie toque el campo.
  - **El masivo del contrato tiene modo propio** (`aplicarCampos: "pax"`): no toca unidad, conductor, hora ni estado, y **no se filtra por hora ni por unidad** —esos filtros protegen la asignación, y los asientos son del contrato—, así que alcanza a los retornos sin marcar "incluir otro horario". `aceptaPax` impide lo caro: una cotización puede tener tres ítems con pax distinto, y sin esa regla corregir uno pisaría la capacidad correcta de los otros dos. Solo se ofrece si el pax se tocó, y marcado solo si hay número: con el campo vaciado el default estaría BORRANDO 30 filas.
  - **La columna PAX del editor de liquidaciones es editable, y escribe la fila autoritativa**: `actualizarPaxContratado` (lib/liquidaciones.ts) manda `reservas.capacidad_contratada` de **todos** los servicios del puente de esa línea y después rehace la descripción de **esa** línea (`recalcularDescripciones(..., { lineas: [id] })` — acotarla es lo que evita pisar las descripciones ajustadas a mano en las otras). Guardarlo solo en `liquidacion_*_linea.pax_contratado` habría sido la trampa: «↻ Recalcular descripciones» lo borra —reconstruye desde la cascada, que no consulta ese renglón— y Programación seguiría mostrando el número viejo. Con la fila autoritativa escrita, recalcular es **idempotente**. **Lo que NO arregla, y la pantalla lo dice**: los meses siguientes. Se escriben los servicios de ESE periodo (los del puente de la línea); los de septiembre son otras filas que nacen del ítem de la cotización. El único escalón que sirve para siempre es la ficha de `cliente_ruta` — y tampoco se escribe desde acá: sería propagar el dato al catálogo de TODO el cliente como efecto colateral de corregir un renglón de un mes.
  - **`guardarReservas` suelta la columna que el error NOMBRA, no un juego fijo.** `COLUMNAS_OPCIONALES` (lib/reservas-pacto.ts) mapea cada columna de migración accesoria a su SQL y a lo que se pierde, y el aviso lo dice. Antes se detectaba cualquier `column … does not exist` pero solo se quitaban las cuatro del Pacto: con cualquier OTRA columna opcional en el patch, el guardado entero moría fila por fila y el mensaje acusaba a dos migraciones que sí estaban corridas. Un ERP al que le falte un SQL accesorio tiene que poder reprogramar un bus igual.
- **`cliente_ruta` no tiene campo «sentido»**: tiene `nombre_ida` obligatorio y `nombre_retorno` opcional, así que una ruta de un solo tramo —y los adicionales del formato son casi siempre de solo retorno— guarda su retorno **como la ida** de la ficha. Ese par canónico es `parCanonicoRuta` y hay que aplicarlo en los DOS extremos; ya falló dos veces seguidas por no hacerlo: al **escribir**, la búsqueda usaba el par crudo y la escritura el canónico, así que la ficha nunca se encontraba a sí misma y a partir del segundo guardado reventaba con `duplicate key value violates unique constraint "uq_cliente_ruta_identidad"`; al **leer**, `clavesCandidatas` seguía preguntando por el par crudo y la ficha recién guardada era invisible — en pantalla, «3 ruta(s) fichada(s)» seguido de «3 ruta(s) sin capacidad contratada» al recargar, que es la peor forma de fallar porque hace dudar de lo que uno acaba de teclear. Guardar y leer son un ciclo: probar una mitad deja pasar justo esto (`scripts/prueba-fichas-ruta.mts`).
- **La fila del modal de fichas es UN ÍTEM, no una ruta entera**: se parte por tarifa, origen y PAX, igual que el ítem, para que lo que se teclea sea lo que va a imprimir ese renglón. **El PAX se escribe SIEMPRE en `reservas.capacidad_contratada`** (`guardarPaxDeServicios`): es el escalón que manda en la cascada, es exacto y no depende de que ningún nombre calce. La ficha `cliente_ruta` es un extra —hereda al mes siguiente— y solo se escribe si la fila es **toda la ruta** (una ficha admite un número por par de nombres) y si sus servicios **se llaman igual** (`LineaAgrupada.nombres_uniformes`). Si la ficha falla, el número ya quedó puesto en los servicios y solo se pierde la herencia: se dice así, no como un fallo de guardado.
  - **EL NOMBRE IMPRESO NO ES UNA IDENTIDAD PARA ESCRIBIR.** El ítem se rotula con el nombre más usado de **cada tramo por separado**, así que con varias redacciones la combinación puede no existir en ningún día: la RUTA B mostraba la ida de las 05:10 junto al retorno de las 17:00, y los del 05:10 vuelven a las 15:00. Fichar con ese par escribía una identidad inventada, la ficha casaba con PARTE de los servicios y —como el PAX separa ítems— **el renglón se partía en dos** justo después de decir "guardado". Por eso el ítem DECLARA `nombres_uniformes` en vez de que la pantalla lo adivine comparando textos.
- **PATRÓN QUE YA COSTÓ TRES FALLOS EN PRODUCCIÓN, TODOS EL MISMO DÍA: escribir con una identidad y leer con otra.** (1) `guardarPaxContratado` buscaba con el par crudo y escribía el canónico → `duplicate key` a partir del segundo guardado; (2) `clavesCandidatas` leía con el par crudo lo que se había escrito canónico → "se guardó" y al recargar "sin capacidad"; (3) el modal fichaba con el nombre IMPRESO del ítem, que puede ser una combinación inexistente → el renglón se partía en dos. La regla que sale de ahí: **si un dato se escribe bajo una clave, la lectura tiene que derivar esa clave por el mismo camino** — y la prueba tiene que cubrir el CICLO, no una mitad. Las tres pasaban con el bug dentro por probar solo la escritura.
- **«↻ Reagrupar ítems»** (`reagruparLineas`) rehace los RENGLONES de un borrador con la agrupación de hoy, sin anularlo: la descripción es un snapshot, así que antes la única salida era anular y volver a cerrar el periodo, lo que además devuelve los servicios al pool. No toca las líneas escritas a mano (reconstruirlas sería borrarlas) ni los servicios; traslada las cantidades fijadas a mano cuya clave sobrevive y **nombra** las que no. Sin transacción, así que **calcula y valida todo antes de borrar**: fallar a mitad deja el documento con menos líneas —roto de forma evidente— en vez de duplicadas y con el total al doble, que puede pasar por bueno. Sus columnas se piden SIN `liquidacion_*_id` por la misma trampa que documenta `resincronizarImportes`. Matriz: `npx tsx scripts/prueba-reagrupar.mts`.
- `normalizarNombreRuta` (TS) debe producir **lo mismo** que `public.fn_norm_ruta` (SQL), que es la expresión del índice único del catálogo.
- La descripción es un **snapshot** en `liquidacion_*_linea.descripcion`: los documentos ya creados no cambian solos. `recalcularDescripciones()` (botón "↻ Recalcular descripciones", solo en borrador) las reescribe desde las reservas de **cada línea**, sin tocar cantidades ni precios. El texto lleva saltos de línea → `white-space: pre-line` en el PDF y `<textarea>` en el editor.
- Todo lo que toca columnas de la fase 03 reintenta sin ellas si la migración no se corrió (cerrar el periodo no puede bloquearse por un dato accesorio del formato).
- **Lo que NO entra al cierre se muestra agrupado POR RUTA y siempre visible** (`fueraDelCierre` en `page.tsx`), no dentro de la tarjeta plegada y recortado a 8 filas de códigos sueltos: con 60 servicios bloqueados eso se leía "y 52 más…" y no nombraba la ruta ni una vez, así que "¿por qué no sale la RUTA A?" solo se podía contestar con una consulta SQL. Incluye las líneas con `cantidad === 0` (`g.sinEjecutar`), que antes se filtraban en silencio.
- **El día se cobra si se prestó CUALQUIERA de sus dos tramos** (`ParServicio.ejecutado`/`.ejecutados`). Mirar solo la cabeza —el tramo que lleva el importe— era una fuga de dinero: con la **ida cancelada** por el cliente y el **retorno prestado**, el día quedaba como no ejecutado y no se facturaba, sin bloqueo y sin aviso. Al puente van solo los tramos realmente prestados, y `servicios[]` referencia un id que SÍ está en `reservas[]` (si no, el conteo de `crearLiquidaciones` restaría).
- **Qué tramo lleva el importe NO es siempre la ida.** La regla es: el que se prestó; a igualdad, la ida. Lo aplican `ModalPrecios`, `ModalCostos` y los avisos. Y `analizarServicios` avisa cuando el importe quedó en un tramo caído mientras el otro sí corrió.
- **Quién es el hermano de un tramo se contesta en UN solo sitio, y por los DOS sentidos del enlace** (`lib/liquidacion-hermanos.ts`). `reserva_vinculada_id` se escribe en los dos lados pero **en dos pasos** (`ModalGenerarPrograma`: primero las idas, después los retornos apuntando a su ida, y recién al final las idas apuntando a su retorno), y borrar un tramo pone en `NULL` el enlace del superviviente (`/programacion`, al eliminar). Basta con eso para que quede escrito en un solo lado — y **seguirlo solo hacia adelante partía el día en dos**: el retorno en S/ 0.00 salía del cierre como "Sin precio de venta", que es el ERP pidiendo **cobrar por segunda vez un día que su ida ya cobra**. Es el error más caro que se puede cometer desde esta pantalla, y la pantalla lo estaba proponiendo. Ahora:
  - `analizarServicios` empareja con un índice **inverso** (`hermanoAqui`), así que el orden en que se procesan los tramos ya no decide nada. Solo empareja hacia atrás cuando es **inequívoco**: con dos filas apuntando a la misma, adivinar sería escribir dinero en el tramo equivocado.
  - Un tramo en S/ 0.00 que no encuentra a su hermano **dentro del grupo** deja de decir "Sin precio de venta" y dice cuál de los cuatro casos es, con su código: `enlace_cruzado`, `tarifa_fuera_del_cierre` (el hermano ya se liquidó en otro documento — el mensaje nombra la liquidación), `tarifa_fuera_del_periodo` (el nocturno que retorna al día siguiente) o `falta_enlace`. Los cuatro salían antes como el mismo rojo.
  - **La pantalla enruta por CÓDIGO, no olfateando el texto** (`bloqueadas[].codigos`). `sinPrecio` solo recoge `sin_precio`: un tramo cubierto por su hermano **no llega al modal de precios**, porque ahí lo único que se puede hacer con él es cobrarlo dos veces.
  - **Lo que falta no es la tarifa, es el enlace**, así que lo que se ofrece es repararlo: botón ámbar **"Enlazar N tramo(s) ida↔retorno"** → `ModalEnlaces.tsx` → `repararEnlaces()`, que escribe **los dos lados** (media docena de sitios del ERP leen esa columna hacia adelante) y **suelta al tercero** que apuntaba a cualquiera de los dos, para no dejar un vínculo de tres puntas. Enlazar **no toca ningún importe**.
  - La **deducción** del par sin enlace (mismo cliente, mismo día, misma etiqueta de ruta, sentido contrario) es la que vivía dentro de `ModalPrecios`, hoisted al módulo para que exista **una** definición de "estos dos tramos son el mismo día". Exige que la etiqueta salga del **nombre** de la ruta: el respaldo `origen → destino` está invertido entre ida y retorno, así que emparejar por ahí sería emparejar por casualidad.
  - **La deducción cuenta el DÍA, no los tramos que sobran** — y esto costó un falso positivo en producción. La primera versión proponía el par cuando quedaban una sola ida y un solo retorno **sueltos**; el 22-08 la RUTA B salió con **dos móviles** y dos de sus cuatro tramos ya tenían enlace, así que los otros dos parecían "los únicos" y se propusieron como pareja: mismo cliente, mismo día, misma ruta, sentidos contrarios, extremos invertidos — perfecto a la vista, y de móviles distintos. Ahora solo se propone cuando esa ruta ese día tiene **una ida y un retorno EN TOTAL**, enlazados incluidos. Los que sobran no dicen cuántas veces salió la ruta.
  - **Con más de un móvil el hermano lo ELIGE un humano**, y ese caso tiene su propio código (`hermano_ambiguo`), que **no** es `sin_precio`: el importe del día está en alguno de los candidatos, así que mandarlo al modal de precios sería el cobro doble por otra puerta. Solo se levanta cuando **algún candidato lleva el importe**; si ninguno lo lleva, lo que falta de verdad es el precio y el bloqueo normal es el correcto. `ModalEnlaces` lista esos tramos **sin marcar**, con un selector de hermano y el detalle de **los otros tramos de esa ruta ese día** (con su enlace actual) — el contexto sin el cual una propuesta no se puede verificar. Es también el único sitio del ERP donde se puede **reasignar** un enlace ya escrito.
  - Un enlace a medias **no bloquea** (el par se arma igual) pero sí **avisa**: el dato sigue roto para Programación y las notificaciones, que lo leen hacia adelante. `ModalServicios` marca la procedencia del hermano (`enlace_a_medias` / `deducido`) en vez de presentarlo como dato escrito.
  - `/programacion` resuelve el hermano por los dos sentidos también (local, y remoto con `.eq("reserva_vinculada_id", id)` cuando el filtro lo dejó fuera): es la pantalla donde se **escribe** el precio, así que un hermano invisible ahí es precisamente donde nace el cobro doble.
  - Matriz: `npx tsx scripts/prueba-hermanos.mts`.
- **`avisosDe` (lib/reservas-pacto.ts) recibe el `hermano`.** Sin él mentía: todo retorno —que va en S/ 0.00 a propósito— disparaba "sin costo pactado", un rojo permanente y falso que enseñaba a ignorar los rojos de verdad e invitaba a cargar el importe dos veces. Ahora distingue *incluido* / *ninguno de los dos* / *los dos* / *el importe está en el tramo cancelado*. Programación además pide confirmación explícita antes de dejar importe en ambos tramos: eso es cobrar (o pagar) el día dos veces, y la liquidación lo lee como dos servicios independientes.
- **Los tres contadores de servicios se abren** (`ModalServicios.tsx`): el `N serv.` del bloque rojo, el `N/N serv.` de cada línea y el `N servicio(s)` de la cabecera del grupo eran solo texto, y cuando el número estaba mal la única salida era ir a Programación a buscar el servicio por código. El modal trae el detalle de Programación (fecha, hora, ruta, placa, conductor, estado, importe, origen) y lo edita en el sitio, en bloque para las filas marcadas. Cuatro reglas que no se pueden aflojar:
  - **Escribe por `guardarReservas`**, la misma puerta que Programación. Un `update` propio sería un cuarto camino con las reglas escritas otra vez.
  - **No propaga el precio a cinco tablas**: escribe la fila autoritativa (`reservas.precio_cliente`) y lo demás se DERIVA. Para el documento que ya existe eso es `resincronizarImportes` (lib/liquidaciones.ts), que sobre un **borrador** relee por el puente las reservas de cada línea con `agrupacion_clave` y reescribe `precio_unitario`, `cantidad_ejecutada`, `cantidad` y `total_linea`. NO toca `cantidad_programada` (el puente solo guarda los tramos ejecutados: reescribirla inventaría un "26/26") ni la `cantidad` que lleva `cantidad_motivo` (alguien la fijó a mano y dejó escrito por qué). Sus columnas se piden SIN `liquidacion_*_id`: esas reservas están dentro de esta misma liquidación y `bloqueosDe` lee ese FK como "ya está en otra", así que pidiéndolo la línea quedaría en cero.
  - **Cuándo se puede editar**: sin liquidar → todo; **borrador** → todo, y al guardar se le vuelve a derivar la línea; **emitida/conformada/facturada** → el importe en solo lectura, con el camino escrito (Reabrir); **anulada** → **editable de nuevo**, porque anular ya devolvió el servicio al pool y bloquearlo dejaría sin arreglo justo el mes que hubo que rehacer. El estado del documento se lee en el modal, no se recibe de la página: la página trae los últimos 200 del lado activo y un servicio puede estar reclamado por uno más viejo.
  - **`avisosDe` acepta `soloJuzgar`** (`"costo" | "precio"`). Programación edita las dos caras y no lo pasa; este modal pide la suya, porque al corregir un precio salían en rojo los avisos del costo del proveedor — ciertos, pero imposibles de atender desde ahí, y un rojo que no se puede arreglar enseña a ignorar los rojos. El aviso del par (el doble cobro) sigue saliendo acotado, y se juzga contra lo que va a quedar guardado, no contra la base: poner importe a los dos tramos en la misma tanda avisa ANTES de guardar.
- **`ModalPrecios` es el espejo, del lado cliente, de `components/pactos/ModalCostos`.** Esa asimetría costó un cierre: un "Sin precio de venta" obligaba a ir a Programación servicio por servicio. Carga la tarifa **por ruta** y solo sobre la **IDA** — el retorno se queda en S/ 0.00 porque la tarifa del par cubre los dos tramos, y escribirla en ambos facturaría el doble.
- **El Anexo 1 va en orden de FECHA, no por línea** (`lib/liquidacion-datos.ts`). Se numera por línea —el ítem `A-01` es lo que ata la fila a la valorización— pero se **imprime** cronológico del día 1 al 31: quien lo revisa lo compara contra su propio calendario, y con una ruta por bloque el mismo día salía cuatro veces separado por páginas. Los dos tramos del día viajan juntos (comparten ítem y una sola tarifa) y el par se ubica en la fecha de su primer tramo, así que el nocturno que retorna de madrugada no se parte. El orden se decide con claves de texto comparadas en binario, no con `localeCompare`, que ignora la puntuación de las fechas ISO. **Sin `SALIDA`, `LLEGADA` ni `KM`**: tres columnas que en producción salían vacías fila tras fila (nadie registra horas reales ni km por servicio) y se comían el ancho del conductor. La columna del ítem se llama `ÍTEM`, no `#`, porque el número **no** es el orden de la fila.
- **La columna PAX del Anexo 1 es la capacidad CONTRATADA, un solo número, y NO se totaliza.** Imprimía `reservas.pasajeros_abordados`, que **no la escribe nadie** —el abordaje vive en `pasajeros_parada`, y la definición de "abordado" es `esAbordado` (lib/documentos-servicio.ts)—, así que salía **0 con el manifiesto lleno**: un cero que el cliente lee como "no viajó nadie" en un servicio que sí se prestó y se le está cobrando. La corrección llegó a imprimir los dos números (contratados / embarcados) y **AFA decidió dejar solo el contratado**: es el que sustenta el importe, y la ocupación del bus —cierta, pero ajena a lo que se valoriza— invitaba en el papel a discutir la factura contra cuánta gente subió ese día. Por eso el conteo del manifiesto se quitó del documento **entero**, con sus dos consultas expandidas (`paradas` → `pasajeros_parada`, que para un mes son miles de filas y obligaban a paginar): el Anexo **2** sigue publicando personas transportadas, que es donde ese dato sí es el tema. Sin dato se imprime `—`, **nunca un cero** (cero asientos contratados no existe), y al pie va `—` en vez de una suma: son los mismos asientos cada día y la ida con su retorno los contarían dos veces, así que el total sería un número que no pactó nadie.
- **La firma y el logo del documento pesan lo que se ve, no lo que se escaneó.** `public/firmaJLCA.png` entró al repo tal cual salió del escáner —3000 × 1842, **2.53 MB**— y se imprime a 38 px de alto en la liquidación y 75 px en el Reporte de Servicio: 48× más resolución de la que llega al papel, descargada en cada documento que se abre. Está a 800 px con paleta de 64 colores (**40 KB**), y el logo de los PDF (`logoafacotizacion-removebg-preview.png`) a paleta de 192 **sin tocar su geometría**, porque ese sí se usa a varios tamaños por toda la app (cabecera de PDF, correos, `/seguimiento`): 140 KB → 23 KB. Al agregar un asset nuevo, mirar a qué tamaño se pinta antes de subirlo.
- **El PDF del CLIENTE no desglosa el valorizado por categoría** (`bloqueValorizacion` en `lib/liquidacion-doc.ts`). "Servicios del periodo", "Adicionales autorizados" y "Falsos fletes (servicios cancelados con acuerdo)" son cortes internos de AFA: el cliente recibe el detalle renglón por renglón en la tabla de arriba (cada adicional rotulado `ADICIONAL`, cada descuento con su cláusula) y abajo solo lo que tiene que cuadrar contra su orden de compra — TOTAL VALORIZADO, IGV y TOTAL A FACTURAR. El **falso flete además no es suyo**: una cancelación se le cobra en S/ 0.00 pase lo que pase, y el avance que se le reconoce al proveedor es un acuerdo entre AFA y el proveedor — enseñárselo, aunque llegue en cero, es enseñarle un trato en el que no es parte. El **descuento sí se imprime**: no es un corte por categoría sino plata que se le resta a ese cliente en esa factura, y callarlo sería bajarle el importe sin decir por qué. El desglose completo sigue en el botón **"Revisar"** (`app/liquidaciones/ModalEditor.tsx`) y en el PDF del **proveedor**, que además lo necesita para la detracción y los anticipos. Un subtotal nuevo por categoría se agrega ahí, no en el formato del cliente.
- **La impresión se arregla en `@page` y en un `<tfoot>`, no en el padding del body** (`CSS_IMPRESION` en `lib/liquidacion-doc.ts`). El documento se imprime desde el navegador y los tres defectos solo aparecían **de la segunda hoja en adelante**, que es justo la que no se mira al diseñar: el padding del body reserva aire arriba de la primera y abajo de la última, así que las intermedias arrancaban y terminaban al filo del papel; el pie `position:fixed` se repite en cada hoja pero **no reserva su sitio**, así que se imprimía encima del último renglón; y las filas se partían por la mitad. Por eso el cuerpo entero va dentro de una tabla de una celda con el pie colgado del `tfoot` — el navegador lo repite al pie de cada página **reservándole el alto real**, que un hueco fijo no acierta porque la banda envuelve a dos líneas según lo largo que sea el domicilio. `.anx tfoot` se fuerza a `table-row-group`: dice "TOTALES DEL PERIODO" y repetirlo se leería como un subtotal de la hoja. Se revisa con `npx tsx scripts/muestra-liquidacion.mts` y mirando el PDF, **no** la primera página en pantalla.

### Filtros del cierre · uno MIRA y dos RECORTAN

`app/liquidaciones/page.tsx` + `lib/liquidacion-clases.ts`. La pantalla tiene ahora dos niveles de filtro y **no hacen lo mismo**, que es lo único importante de esta parte:

- **Contraparte** (fila 1, el de siempre): elige qué TARJETAS se ven. Cada contraparte es su propio documento, así que aislar una no cambia nada de lo que se emite. Sus opciones se cuentan sobre el pool ENTERO (`enCola`), nunca sobre lo ya filtrado: un proveedor cuyo mes es todo eventual tiene que seguir en la lista mientras el filtro dice "Fijos", o el filtro se vuelve una trampa sin salida.
- **Cruce y clase** (fila 2, "Dentro del proveedor"): cortan DENTRO de la tarjeta, así que **el documento que se emita contiene solo lo que quede**. Es un caso de uso real —pagarle a un tercerizado lo de un cliente en un documento y lo del otro en otro— pero es también la forma nueva de emitir media liquidación por descuido, así que: aviso ámbar *"Cierre parcial: N de M"* **dentro de la barra pegajosa** (el olvido pasa con scroll hecho, cuando el filtro ya no se ve), `confirm()` al liquidar, y **la selección se borra al mover cualquiera de los dos** — por lo mismo que se borra al mover el periodo: no cambia qué grupos hay, cambia lo que cada grupo CONTIENE.
- **El cruce es la OTRA punta**: el CLIENTE en la pestaña de pagar (un proveedor mueve a varios clientes en el mismo mes y la tarjeta no nombraba a ninguno) y el PROVEEDOR en la de facturar, con la flota propia como la clave `"sin"`.
- **Se filtra por DÍA, nunca por tramo.** Un filtro que dejara pasar la ida y no el retorno partiría el día en dos y el superviviente saldría "Sin precio de venta" — pidiendo cobrar por segunda vez lo que su hermano ya cobra, el error más caro de este módulo. Por eso `pasaCruce` acepta el día si lo cumple CUALQUIERA de los dos tramos, y la clase la declara el tramo que **lleva el importe** (`claseDeTramos`, la misma regla de `origenDelPar`: quien cobra, clasifica; un retorno mudo marcado a mano no mueve nada).
- **`ClaseServicio` son dos ejes, no un campo**: `tipo_servicio_detalle` dice fijo vs. eventual (misma lista `TIPOS_SERVICIO_FIJO` que usan /programacion, /monitoreo, /calendario, /seguimiento, `lib/notificaciones` y `lib/descarga-masiva` — cada uno con su propia copia, ojo al tocarla) y `origen_contractual` dice contrato vs. adicional. **La marca escrita gana**: un eventual marcado adicional sale como adicional. Sin tipo escrito → eventual, como en el resto de la app.
- **Cada desplegable se cuenta con el OTRO filtro puesto y sin el suyo.** Aplicándose el suyo, la lista de clientes se quedaría con el cliente ya elegido y no habría forma de cambiar de cliente sin quitar antes el filtro.
- **Las etiquetas por cliente de la tarjeta se atribuyen por LÍNEA**, para que sus importes sumen exactamente el total del grupo. Una línea que mezcla dos clientes (la agrupación junta por ruta y tarifa, no por cliente) sale como "Varios" en vez de repartirse a medias. Y como un servicio BLOQUEADO no llega a ser línea, el bloque rojo "No entran a la liquidación" nombra también de quién es cada fila: si no, los 13 servicios con problema de un proveedor no tendrían dueño en ninguna parte de la pantalla.
- Matriz: `npx tsx scripts/prueba-clases.mts`.

### Cancelaciones y falso flete · el default cae del lado del error reversible

`supabase/reservas-05-falso-flete.sql` + `montoDe`/`bloqueosDe` en `lib/liquidacion-agrupacion.ts`. Un servicio cancelado no se cobra ni se paga, y el ERP no sabía decirlo: el importe se quedaba escrito en la reserva y nada distinguía un acuerdo de un descuido.

- **UNA CANCELACIÓN VALE S/ 0.00. El importe, por sí solo, NO autoriza nada.** Solo se paga con `falso_flete = true`, un dato que alguien escribió DESPUÉS de saber que el servicio se canceló. La tentación era deducirlo (cancelado + importe > 0) y avisar en ámbar; es la decisión equivocada y la razón es de negocio, no de código: **pagar de menos lo reclama el proveedor y se corrige; pagar de más hay que pedir que lo devuelvan, y no vuelve.** Como el importe huérfano es JUSTO el que deja el error humano de cancelar sin borrar el costo, deducirlo habría convertido cada descuido en un pago — y un ámbar que sale todos los meses se vuelve paisaje. El `default false` de la migración es lo que hace segura la transición: todo lo cancelado que ya existe pasa a 0 sin que nadie lo revise.
- **La regla vive SOLO en `montoDe`**, y de ahí derivan los bloqueos, quién es la cabeza del par, el precio unitario del renglón y los totales. Con la regla repartida, un servicio podía valer 0 para el bloqueo y S/ 664.41 para el documento. `precioUnitario` la usa también, por lo mismo.
- **El falso flete es del PROVEEDOR. Al cliente no se le cobra la cancelación** (decisión comercial de AFA), así que del lado cliente `montoDe` devuelve 0 y no hay marca que lo cambie: ofrecer la casilla sería ofrecer algo que la empresa decidió no hacer. `ModalServicios` solo la pinta en la pestaña de pagar.
- **El motivo es obligatorio** y bloquea el guardado, como `adicional_motivo`: es la única constancia de por qué salió dinero por un viaje que no se prestó. Se pide en la misma celda que la casilla, y **marcar y poner el monto son un solo acto** — si el importe se tomara del que ya estaba, se pagaría el número que dejó el error (S/ 664.41 completos donde el acuerdo eran S/ 120).
- **UN MISMO ROJO DECÍA TRES COSAS.** `bloqueosDe` recibe ahora los tramos del DÍA y las separa: `sin_costo`/`sin_precio` (el día corrió, falta el importe → rojo), `cancelado_sin_pago` (el día entero se cayó → gris, no es trabajo, no alimenta el botón de importes faltantes) y `no_cerrado` (nadie lo cerró → rojo, pero el arreglo es cerrarlo). El tercero era el peligroso: mandaba a **cargarle un costo a un viaje que quizá no ocurrió**, que es crear una cuenta por pagar de la nada. `bloqueoEsTrabajo` es lo que la pantalla usa para el tono; `avisosDe` calla los avisos de dinero cuando el día entero se cayó sin acuerdo, por lo mismo que ya calla el del retorno en S/ 0.00.
- **El falso flete es su propia línea, con su propio subtotal** (`tipo: "falso_flete"`, *"Falsos fletes (servicios cancelados con acuerdo)"*). Como `servicio` inflaría la cantidad que el proveedor coteja contra su factura; como `adicional` rotularía de "pedido de más" lo contrario; y `penalidad`/`descuento` no sirven porque `totalesValorizacion` los RESTA. Entra en el **cubo** de `agruparPorRutaContratada` (`|ff`) igual que la tarifa y el pax, así que no puede fundirse con los servicios prestados de su ruta ni a idéntico precio; `agruparServicios` lo verifica y **lanza**.
- **`cantidad_ejecutada` de un falso flete son los días acordados, no cero.** Cero sería literal y a la vez inútil: la línea saldría descartada (que es lo que pasaba antes — **el avance pactado no lo pagaba ningún documento**) y el editor exigiría "motivo del ajuste" en un renglón que no ajusta nada.
- **Al puente van los DOS tramos del día**, y es la única excepción a "solo los prestados": no hay ninguno prestado y el día SÍ se saldó, así que sin reclamarlos volverían al pool el mes siguiente y se pagarían dos veces. Queda `estado='cancelada'` (el bus no salió) y `estado_proveedor='conciliada'` (ya se saldó): son las dos dimensiones independientes de `lib/estados.ts`, y esto es justo para lo que existen.
- **El importe huérfano ya estaba ensuciando el margen**, no solo el cierre: `v_costo_servicio` y `v_egresos` leen `reservas.costo_proveedor` sin preguntar si el servicio se prestó. Por eso la pantalla ofrece **"Poner en S/ 0.00"** con el monto y el conteo a la vista — lo pulsa una persona, escribe por `guardarReservas` con motivo `correccion_carga` y deja acta. **Nunca un UPDATE masivo automático sobre dinero.**
- Matriz: `npx tsx scripts/prueba-falso-flete.mts`. Medición sobre datos reales (solo lee): `npx tsx scripts/diagnostico-cancelados.mts 2026-08-01 2026-08-31`.

**LA OTRA MITAD: el importe huérfano deja de NACER** (`lib/reservas-cancelacion.ts`, motor PURO). Todo lo de arriba puso a salvo el dinero en el CIERRE, pero el dinero se escribe en `/programacion` — y ahí no había nada: se cancelaba un servicio con S/ 664.41 de costo cargado y el importe se quedaba escrito, sin preguntar y **sin forma de marcar el acuerdo desde esa pantalla** (la casilla solo existía en `/liquidaciones → ModalServicios`, pestaña de pagar). El propio `avisosDe` decía *"márcalo como falso flete"* sobre una pantalla que no podía marcarlo. Y el dato sucio no esperaba al cierre para hacer daño: `v_costo_servicio` y `v_egresos` lo leen sin preguntar si el servicio se prestó, así que el margen ya estaba mal. La limpieza vivía una pantalla más allá, o sea: **el dato nacía en el origen y se saneaba en la desembocadura, una vez al mes y si alguien lo notaba.**

- **Se pregunta AL CANCELAR**, que es el único momento en que quien cancela sabe si el bus llegó a salir. Dos caminos: *no salió* → S/ 0.00 (el default, el lado reversible del error, mismo criterio que el `default false` de la migración) o *salió y hay acuerdo* → falso flete con monto y **motivo obligatorio, que BLOQUEA el guardado** — aquí no se está despachando un bus, se está autorizando un pago.
- **EL MONTO SE TECLEA, NO SE HEREDA.** El importe cargado es el del servicio completo que no se prestó: copiarlo pagaría S/ 664.41 donde el acuerdo eran S/ 120. Es la misma regla que ya aplicaba `ModalServicios` ("marcar y poner el monto son un solo acto"), y por eso el avance tiene su propio campo en vez de reusar el de costo. **Sí** se precarga cuando el acuerdo YA está escrito: ahí no es el número del error, es el que alguien pactó.
- **NO SE LIMPIA A CIEGAS, y esto es lo que impide una fuga de dinero de las caras.** Poner en S/ 0.00 todo tramo cancelado con importe borraría la tarifa de un día trabajado: con la **ida cancelada** y el **retorno prestado** el día SÍ se factura, y su importe está escrito justo en la ida caída ("qué tramo lleva el importe no es siempre la ida: es el que se prestó"). El plan solo limpia cuando el DÍA ENTERO se cayó —el mismo `diaCaido` de `avisosDe`— y en el otro caso devuelve `importe_del_dia_vivo` con el patch **vacío**: ahí no falta limpiar, falta MOVER el importe, que es lo que ya dice `avisosDe`.
- **Al cliente se le retira el precio igual, con acuerdo o sin él**: la cancelación no se le cobra pase lo que pase, y el avance es un trato entre AFA y el proveedor en el que el cliente no es parte. El falso flete solo se ofrece en **tercerizado**: la flota propia no tiene proveedor a quien pagarle, y `normalizarAsignacion` ya le pone el costo en cero.
- **La marca se retira sola si el servicio deja de estar cancelado** (misma regla que `ModalServicios`): una marca colgada de un servicio prestado no describe nada.
- **HAY DOS PUERTAS QUE CANCELAN, y las dos preguntan.** El formulario y el desplegable de estado de la fila (`cambiarEstadoRapido`, que escribe con un `update` directo). La fila decide con **el mismo `planDeCancelacion`**, no con una condición propia — dos definiciones de "esto hay que decidirlo" es cómo una se queda atrás. Sin importe la cancelación rápida **sigue siendo rápida** (el 90 % de los casos); con importe manda al formulario, donde el hermano se busca en la base y el veredicto se rehace con la verdad completa. Errar hacia el formulario cuesta un clic; errar hacia el update directo deja el huérfano.
- **Los dos candados de dinero CALLAN en un día caído** (el del doble cobro y el de "sin costo pactado"): ahí no hay nada que cobrar dos veces ni ningún costo que falte: el plan está retirando los importes. Es el mismo silencio que `avisosDe` aplica, y por lo mismo — un aviso que salta cuando el sistema hace lo correcto enseña a hacer clic sin leer.
- **`avisosDe` recibe el patch del plan, no el formulario crudo**: si no, un día caído seguía pidiendo "márcalo como falso flete" con la casilla ya marcada tres centímetros más arriba.
- Matriz: `npx tsx scripts/prueba-cancelacion.mts` — 34 casos, con la **invariante dura comprobada sobre 864 combinaciones**: ningún patch guardable escribe un costo > 0 sin la marca y su motivo en el mismo patch. Y su corolario: con el hermano prestado, **ninguna** decisión toca el importe.

### Servicios adicionales · lo que se pide POR ENCIMA del contrato

`supabase/reservas-04-servicios-adicionales.sql` + el modo `adicional` de `components/programacion/ModalGenerarPrograma.tsx`. **No existe una tabla `contratos`: el contrato es la cotización con `modo_servicio='fijo'`,** y el adicional queda amarrado a ella por el `cotizacion_id` que la reserva ya guarda. Por eso NO hay pantalla nueva ni correlativo `AD-`: hay un botón **"Adicional"** al lado de "Programa fijo" que abre **el mismo modal** con `modo="adicional"`. Dos pantallas que generan servicios desde una cotización serían la misma regla en dos sitios, y terminarían diciendo cosas distintas.

- **Lo que cambia en modo adicional, y solo eso:** fechas **sueltas** (no rango × días de la semana), **sentido a elección** (`ida | retorno | ambos` — antes, si la cotización tenía `hora_retorno`, se creaban SIEMPRE los dos tramos y "una salida adicional" obligaba a cancelar la entrada a mano), **precio editable** prellenado con el cotizado y mostrando la diferencia, **motivo obligatorio solo si el precio difiere**, y **un solo móvil** (si la cotización tiene tres ítems se elige cuál: generar los tres crearía tres servicios donde el cliente pidió uno).
- **Por qué el precio se pone AL GENERAR y no después:** un adicional **nace** con su precio, y el acta de venta (`fn_reservas_pacto_acta`) vive en el `AFTER UPDATE`. Corregir el precio después de crearlo dispara esa maquinaria — y además revienta con `gen_random_bytes` si no se corrió `pacto-03-fix-token-pgcrypto.sql`. Nacer con el precio no dispara nada, que es lo correcto: el adicional no encarece nada, se cobra lo que se acordó. Como contrapartida, `adicional_motivo`/`adicional_nota` son el **único** sitio donde queda escrito el porqué. (Ese mismo `AFTER UPDATE` emitía además el enlace público de conformidad; ya no — ver abajo.)
- **`origen_contractual` entra en la clave de agrupación de la liquidación.** Sin él, una salida adicional de la RUTA A cobrada a la tarifa del contrato se sumaba a la línea del contrato y dejaba de existir: el cliente leía "23 servicios" donde había 22 contratados y 1 pedido aparte. La línea sale con `tipo: "adicional"`, que es lo que llena el subtotal **"Adicionales autorizados"** del AFA-FL-07 — hasta ahora solo se podía llenar escribiendo el importe a mano en el editor. Los adicionales se ordenan **al final** y la descripción arranca con `SERVICIO ADICIONAL`, porque esa descripción se copia a correos y órdenes de compra, donde el color del renglón se pierde.
- **`tipo === "servicio"` dejó de significar "tiene reservas detrás".** Un adicional generado desde Programación también las tiene. El discriminante correcto es `agrupacion_clave` (`deReservas` en `ModalEditor`, el filtro de `recalcularDescripciones`, y el candado de `eliminarLinea`, que ahora cuenta el puente en vez de mirar el tipo: borrar esa línea dejaría reservas marcadas como liquidadas sin nada que las cobre).
- **El adicional no ensucia la referencia de precios.** `ModalPrecios` propone "la última vez que cobraste esta ruta": un adicional de S/ 480 por una unidad mayor se descarta de esa sugerencia.
- **El origen del día lo declara EL TRAMO QUE LLEVA EL IMPORTE** (`origenDelPar`). Antes CONTAGIABA: bastaba con marcar un tramo para que el día entero saltara al subtotal de adicionales. La intención era no cobrar como contratado un día pedido aparte, pero significaba que marcar el retorno —que va en S/ 0.00 a propósito— movía la tarifa completa de subtotal sin que nadie lo pidiera, mientras la pantalla seguía diciendo "Contrato" sobre la ida. Es la regla de oro aplicada al origen: quien cobra, clasifica. Por eso **se puede cambiar un tramo suelto** ("Cambiar solo el tramo marcado" en el modal de origen), y `efectoDeMarcarTramo` dice ANTES cuál de las dos cosas va a pasar — mover el día de subtotal, o dejar la valorización intacta y quedar como registro de ese tramo. Cuando los dos tramos difieren, `analizarServicios` **avisa**: la marca del tramo mudo no se pierde en silencio.
- **Reclasificar arrastra al hermano POR DEFECTO, y para la etiqueta mal puesta está el CANJE** (`lib/reservas-canje.ts` + el modo canje del modal de origen en `/programacion`). Lo normal sigue siendo que los dos tramos queden del mismo lado: la unidad que se cobra es el día. Cuando la etiqueta no sobra sino que está en el servicio equivocado —dos servicios que se intercambiaron las unidades por una contingencia— lo correcto es cambiar **los dos a la vez**: uno pasa a adicional y el otro vuelve a contrato, con neto cero sobre la valorización. El canje respeta "solo el tramo marcado": intercambia los tramos elegidos, no los días enteros. `planDeCanje` calcula ese neto y avisa de lo que no se ve (intercambio asimétrico 2 tramos contra 1, un lado en S/ 0.00, subtotal que se mueve); el modal lo muestra **antes** de aplicar. Motivo y nota son **obligatorios** ahí: el lado que vuelve a contrato limpia `adicional_motivo`/`adicional_nota` (describirían un adicional que ya no existe, y `v_adicionales` ni los publica), así que la nota del lado adicional —que nombra a su contraparte por código— es el **único rastro** del intercambio. No hay transacción: si el segundo lado falla, el canje queda a medias con los dos servicios del mismo lado y **se dice cuál cambió y cuál no**, en vez de revertir a ciegas un motivo que la lista no trae. Motivo nuevo `intercambio_contingencia`, con `lado: "venta"` para que salga solo en este modal y no en el de edición.
- `contingencia` está en el CHECK desde el día uno aunque no tenga pantalla: ampliar un CHECK sobre `reservas` obliga a revalidar la tabla entera.
- **Todo lo que toca estas columnas reintenta sin ellas** (`COLUMNAS_OPCIONALES` en el modal, `COLS_OPCIONALES` en `/programacion`, la cascada de `.catch()` en `/liquidaciones`). Con una diferencia: si al generar un adicional se cae `origen_contractual`, **se avisa en pantalla** — los servicios se crearon pero nacieron indistinguibles del contrato, y callarlo dejaría al operador buscando un subtotal que nunca va a aparecer.
- Matriz: `npx tsx scripts/prueba-adicionales.mts`. Vista para reportes: `v_adicionales` (no agrega nada; los cortes los hace quien consulta).

### La firma del cliente se pide UNA vez por periodo, no por servicio (Pacto fase 06)

`supabase/pacto-06-sin-conformidad-de-cambio.sql`. **Hay DOS conformidades en el ERP y solo una sigue viva.** La del **cierre** (`/liquidaciones` → "✉ Enviar" → `/conformidad/[token]`) es la que sustenta la factura y no se toca. La del **cambio de precio** (`/conformidad-cambio/[token]`) se emitía SOLA en el `AFTER UPDATE`: cada vez que a un servicio ya creado se le subía el precio, el acta de venta nacía con un token y se quedaba en `/pactos → Conformidades` esperando que alguien se lo mandara al cliente. Está apagada.

- **Por qué.** Es pedir la misma plata dos veces por dos puertas. En un contrato fijo, una avería a media semana y dos cambios de unidad son tres enlaces sueltos al mes, de pocos soles cada uno, a la misma persona que en veinte días firma la valorización con todo dentro. El cliente deja de abrirlos, y el que se quema es el enlace del cierre, que es el que sí importa.
- **Se apaga con la POLÍTICA, no reescribiendo el trigger**, y esto es lo que hay que entender antes de tocarlo: `fn_reservas_pacto_acta` está **duplicada** en el repo (`pacto-03-triggers.sql` y el parche `pacto-03-fix-token-pgcrypto.sql`) y desde una migración no se sabe cuál quedó instalada. Las dos consultan `coalesce(pol.exige_conformidad_cliente, true)` antes de emitir el token, así que bajar la bandera funciona con cualquiera de las dos. Una tercera copia del cuerpo solo agrega otra versión que puede desincronizarse — el propio parche documenta lo caro que salió eso. Además, dejar la bandera en `true` mientras el código ignora la conformidad sería una fila que dice una cosa y un sistema que hace otra, que es el error que este ERP ya pagó tres veces. **Se revierte con un UPDATE, no con un despliegue.**
- **EL ACTA DE VENTA SIGUE ESCRIBIÉNDOSE ENTERA.** Quién subió el precio, de cuánto a cuánto, cuándo, con qué motivo y con qué efecto en el margen: eso es `servicio_pacto` y nunca dependió del enlace. La trazabilidad del cambio es interna; el enlace era solo el papel del cliente. Se ve igual en `/pactos → Historial`.
- **Las conformidades ya FIRMADAS no se tocan.** La migración retira solo las `pendiente` (token a `null`, estado a `no_aplica`); `conforme` y `observada` conservan token, firmante y fecha, porque sostienen el cobro de ese diferencial. Los importes del acta no se tocan nunca.
- **El aviso de `avisosDe` se fue con el enlace que anunciaba**, y no se reemplazó por otro: subir el precio ya pide su motivo en la misma pantalla. Ruido de más en ese panel se paga caro — es el mismo sitio donde sale el aviso de que el día se está cobrando DOS VECES. `scripts/prueba-pacto.mts` lo fija por el CONCEPTO (`/conformidad|enlace/`), no por la frase: un texto nuevo que vuelva a prometerle algo al cliente desde ahí tiene que hacer fallar la prueba.
- **La pestaña `Conformidades` se queda, como archivo**, y su estado vacío **lee la bandera** en vez de afirmar una frase fija: antes decía "se genera un enlace automáticamente cada vez que sube el precio", que con la emisión apagada es la pantalla mintiendo sobre lo que hace el sistema. Sin nada pendiente muestra el archivo completo (filtrar por pendientes dejaba la pantalla en blanco con las filas cargadas detrás). La ruta pública `/conformidad-cambio/[token]` y `/api/pactos/conformidad` **no se borran**: son cómo se abre una conformidad ya firmada.

### Semáforo de puntualidad · el siguiente paradero es un HECHO, no un botón

`lib/retrasos.ts` (motor PURO) + `lib/retrasos-datos.ts` (el que lee) + `/api/seguimiento/retrasos` (la torre, no paga ETA) + `/api/alertas-flota/tick` (el que paga y el que AVISA por WhatsApp). El módulo ya nacía con la doctrina buena —tri-estado, nunca se afirma un retraso por AUSENCIA de evidencia— pero contestaba "¿cuál es el siguiente paradero?" con `paradas.find(p => p.estado !== "completada")`, que es **exactamente la definición que la cabecera de `lib/avance-paradas.ts` declara rota**: no dice por dónde va el bus, dice si un humano tocó un botón.

- **El fallo medido** (SNACKS AMERICA LATINA, reserva #25526, 09-09-2026 23:05): el modal decía *"2 parada(s) pasada(s) sin marcar · próxima Puente Santa Anita, a 1.4 km, llega 23:05"* y la fila de abajo, **en la misma pantalla**, *"TARDE EN RUTA +47' · llegará tarde a Bertello · a 13.9 km · ETA 23:27 vs 22:40 plan"*. Los 13.9 km eran la distancia a un paradero YA PASADO, así que **el retraso CRECÍA cuanto mejor iba el servicio**: cada kilómetro de avance por la ruta engordaba el número. Y no era pintura — el bloque 4b del tick manda ese veredicto al directorio.
- **NO se escribió un segundo motor de avance: se le pasa el del primero.** `retrasos-datos.ts` siembra `lib/avance-paradas.ts` (el MISMO que consume `ModalGps` y `/api/cliente/gps`) y le entrega a `evaluarPuntualidad` el conjunto `paradasPasadas`. Dos motores que contestan la misma pregunta terminan contestando distinto, que es literalmente el bug: las dos mitades del tablero contradiciéndose.
- **Viaja por ID, jamás por índice.** El motor de avance indexa por posición y quien lo llama ordena las paradas por su cuenta; emparejar por índice es el fallo que este repo ya pagó tres veces (ver *"escribir con una identidad y leer con otra"*). Se ordena y se lee del MISMO array, y hacia fuera solo salen ids.
- **Es ADITIVO, nunca sustractivo**: es `piso = max(pisoConductor, pisoGps)` visto desde el otro lado. Una parada `completada` sigue pasada aunque el GPS no la traiga (el conductor marcó y el bus no tenía señal). El botón nunca se contradice.
- **Solo `en_curso`, y solo con los fixes de ESA reserva** (`reserva_id`), nunca el respaldo por conductor/vehículo que usa `fixesDe`: la huella del viaje anterior pasa por los mismos paraderos y dispararía el piso hasta el final de la ruta. Antes de arrancar, el objetivo es el paradero de ORIGEN y el piso tiene que ser 0 por definición.
- **La huella ENTERA, paginada, no una ventana reciente.** El motor sube el piso de a una parada real (candado `hayRealAntes`): sembrado desde la mitad del recorrido, las paradas iniciales nunca se declaran pasadas y el piso se queda atascado en la primera — o sea, el mismo bug por otra puerta. Se corre **sin la polilínea** (el veto geométrico), igual que `/api/cliente/gps`: traerla es una llamada a Google por servicio y este camino no paga; el veto solo RESTA veredictos, así que su ausencia no inventa paradas pasadas.
- **Todo el camino es best-effort**: cualquier fallo devuelve `[]` y el veredicto sale como siempre, mirando solo el botón. Un SQL lento no puede dejar a la torre sin semáforo.
- **Cuando el GPS mueve el objetivo, la evidencia lo DICE** (`objetivo por GPS (X sin marcar)`), y solo entonces: es el caso en que el app del conductor sigue mostrando otro paradero como pendiente, y sin esa línea la torre parece estar hablando de otro servicio. Un aviso que sale siempre se vuelve paisaje.
- **Sin objetivo hay DOS mundos y colapsarlos mandaba a arreglar lo que no estaba roto**: `ya pasó todos los paraderos del recorrido` (el servicio termina, solo falta cerrarlo) vs. `sin paradas pendientes con coordenadas` (falta geocodificar, se arregla en la ficha de la ruta). El motivo se DECLARA, no se olfatea.
- **Lo que NO se aflojó, y es la mitad que importa**: un retraso de verdad sigue saliendo, contra el paradero correcto y con los minutos reales. Callarlo sería peor que el falso positivo.
- Matriz: `npx tsx scripts/prueba-retrasos.mts` — trae el caso #25526 dentro, **conserva el bug como prueba de regresión** (si deja de reproducir, el escenario dejó de ser el que se rompió) y fija que sin dato de avance el veredicto es idéntico al de antes.

### Lectura del odómetro · el dígito de más (`lib/odometro-seleccion.ts`, `lib/vision-ia.ts`)

**El ERP sabe cuántos dígitos tiene el odómetro de cada unidad y se lo estaba callando.** El caso real (CUP-435, 05/09/2026): el tablero marca `ODO 23980 km` / `TRIP 388.0` y la IA devolvió **239.980** en dos lecturas seguidas. Un dígito de más, diez veces el número, y el km de una unidad envenena después el vencimiento de mantenimiento y el rendimiento km/gal de todos sus tramos.

- **LA FORMA DEL NÚMERO ES UN HECHO DE LA BASE; LA GUÍA DEL TABLERO ES UNA OPINIÓN QUE ALGUIEN TECLEA. No las ates.** La línea *"el odómetro TOTAL de esta unidad es un número de N dígitos"* (N sale de `kilometraje_actual`) viajaba **dentro** del bloque de `vehiculos.guia_odometro`, texto libre que se escribe a mano en `/radar-ia → Configuración`. El route la calculaba siempre y la tiraba: sin guía escrita —o sea, en casi toda la flota— el modelo leía el tablero sin saber cuántas cifras esperar. Es la causa, y estaba en los **dos** carriles de lectura: `bloqueFormaOdometro` (lib/vision-ia.ts, el de `/mantenimiento`, `/tercerizadas` y la app del conductor) y `cargarGuiasOdometro` (lib/radar/motor.ts, que además filtraba `.not("guia_odometro","is",null)`, así que esa unidad ni se cargaba). Ahora entra la unidad que tenga **cualquiera de las dos**.
- **Al prompt va la FORMA, jamás el km exacto.** Un número exacto en el prompt es un número que el modelo copia cuando no logra leer la foto, y ese eco es indistinguible de una lectura buena — por eso `elegirOdometro` trae además un guard anti-eco (≤ 2 km del vigente = sospechoso, no lectura).
- **Quien LEE y quien ESCRIBE tienen que decir lo mismo del mismo número.** `elegirOdometro` (decide si el número se pre-llena en la pantalla) dejaba el techo en `Infinity` cuando la unidad no tenía ninguna lectura **viva**, así que un ×10 salía "en banda" y se ofrecía como bueno… para que `evaluarLectura` (decide si se guarda), tres líneas después, lo marcara *"Salto ×10: posible dígito de más"*. `RATIO_DIGITO_DE_MAS`/`PISO_RATIO_DIGITO` se exportan de `lib/odometro.ts` y los aplican los dos. El piso de 5.000 km no se toca: por debajo, un ×8 legítimo existe (unidad nueva) y un dígito de más siempre deja el vigente alto, así que no se pierde el caso.
- **`hayHistorial === false` NO es solo "unidad nueva": es "sin ninguna lectura aceptada".** Una unidad cuyas lecturas van todas a sospechosa se queda sin ninguna viva, y con el techo en `Infinity` el agujero **se realimentaba**: el segundo dígito de más entraba tan liso como el primero. Eso es exactamente lo que se reportó ("los 2 últimos").
- **EL DÍGITO QUE SOBRA ESTÁ DUPLICADO, y eso SÍ se puede deshacer** (`corregirDigitoRepetido`). Medido sobre los cuatro casos reales de la flota, el modelo no inserta una cifra cualquiera: **repite una que ya estaba**. `23980→239980` · `23379→233379` · `560473→5600473`; y `2320206`, que no tiene dos cifras adyacentes iguales, no se toca. La diferencia entre esto y recortar por donde cuadre está **medida**: borrando cualquier dígito caen en la banda 3, 3, 0 y 4 candidatos; colapsando solo los repetidos, 1, 1, 0 y 1. La ambigüedad desaparece porque la hipótesis es concreta («esta cifra se leyó dos veces»), no un barrido de posiciones. Dos condiciones obligatorias, las mismas de `coherencia-voucher.ts`: el arreglo tiene que ser **exacto** (colapsar una repetición) y **único** (con dos colapsos dentro de la banda no se elige ninguno).
- **UN NÚMERO DEDUCIDO NO ES UNA LECTURA, Y NO SE ACEPTA SOLO.** `confirmar: true` marca la diferencia con `parcial`: ahí el modelo SÍ transcribió el número del tablero y solo lo puso en el campo equivocado; aquí el ERP reconstruye una cifra que nadie escribió. En las tres pantallas se **pre-llena** con los DOS números a la vista («la IA leyó 239.980, se propone 23.980 — compruébalo contra la foto»), porque la persona tiene la foto delante justo en ese momento. En el **Radar**, que graba sin nadie mirando, `registrarLectura({ forzarRevision: true })` guarda la lectura con su foto y el número corregido pero la deja **sospechosa**: no mueve `vehiculos.kilometraje_actual` hasta que alguien la acepte. Un km inventado envenena el vencimiento de mantenimiento y el rendimiento km/gal de todos los tramos siguientes.
- **Cuando NO hay repetición, no se adivina**: sigue el `codigo: "digito_de_mas"` con las dos cantidades de dígitos y el rango, en vez del genérico *"imposible para esta unidad"*. Mismo criterio que `cuadre_ambiguo`.
- **La pantalla enruta por CÓDIGO** (`codigo_seleccion` en la respuesta de `/api/mantenimiento/leer-odometro`): `digito_repetido` · `digito_de_mas` · `fuera_de_banda` · `eco` · `parcial`. Los tres consumidores (`OdometroTab`, `OdometroTerceroModal`, app del conductor) titulan con él.
- **En el prompt va el patrón real, no uno genérico**: *"NO REPITAS UN DÍGITO"* con los tres casos medidos, en `PROMPT_ODO` y en `CASO_ODOMETRO`. Y ante la duda de si son una o dos cifras, `km: null` — una lectura menos no cuesta nada.
- **El odómetro de una RECARGA se corrige donde se revisa la recarga** (`/radar-ia?tab=combustible`). El panel de revisión editaba fecha, unidad, grifo, tipo, cantidad, precio y monto — todo menos el kilometraje, que se registraba tal cual con `c.kilometraje ?? 0`. Era el único dato de la fila sin arreglo posible desde ninguna pantalla, y justo el que envenena después el km/gal de la unidad y el vencimiento de su mantenimiento. Ahora es un campo más, con tres reglas:
  - **Se escribe por `registrarLectura`**, la misma puerta que `/combustible` y que el auto-registro del Radar. La rama manual **no alimentaba `lecturas_odometro`**: la recarga que pasaba por revisión —la que un humano sí miró— dejaba su km dentro de la carga y no llegaba ni al km vigente ni a `/mantenimiento`. No se fuerza nada: el anti-retroceso decide y la pantalla **reporta el veredicto** (`sospechosa` + motivo) en vez de tragárselo.
  - **El `idemKey` es por FILA del Radar (`radar_odo_comb_rev:<id>`), nunca por mensaje.** Una ráfaga con dos vouchers deja dos filas con el mismo `mensaje_id` (`insertarRecargasAdicionales`), así que una clave por mensaje habría dado la segunda lectura por "ya registrada" y la habría perdido entera. Por lo mismo `registrarLectura` devuelve `duplicada`: sus tres dedupes (idem, URL de foto, hash) devolvían la fila vieja como si acabaran de insertarla, y la pantalla decía "registrado" sobre un número que no se guardó.
  - **El aviso del campo comparte constantes con quien escribe** (`revisarKmTecleado`, en `lib/odometro-seleccion.ts`) y se limita al salto de orden de magnitud: es la única rama de `evaluarLectura` que depende solo del km vigente —el máximo histórico, que nada legítimo multiplica por ocho—. "Menor al vigente" **no** se pinta: un voucher de hace tres días procesado hoy es legítimo, y ese ámbar saldría en filas correctas. Debajo del campo va el km vigente de la unidad elegida, **sin botón «usar este»** (mismo criterio que el PAX de `/programacion`): copiar el vigente sería fabricar una lectura que nadie tomó. Vacío es un dato — se registra `0`, que es como el resto del ERP escribe "sin odómetro" en esa columna, y la pantalla dice qué se pierde con eso. La corrección entra al dataset (`campo: "kilometraje"` en `radar_combustible_correcciones`) y de ahí al prompt de la próxima foto.
- **El veredicto sigue sin bloquear el registro.** Ni aquí ni en el Radar: una lectura que no llega a ser fila desaparece de "Lecturas por revisar", que es donde el operador la corrige y donde nace el dataset de `odometro_correcciones` (`ia_digito` → `leccionesOdometro` → el prompt de la próxima foto).
- Matriz: `npx tsx scripts/prueba-odometro.mts` — trae los **cuatro casos reales** con su valor esperado (y el de la CUP-435 del 05/09 se comprueba contra lo que dice la foto), la sección que fija que **lo legítimo sigue pasando** (unidad nueva, salto tras un hueco largo, rescate del trip de BUI-272, y un km legítimo CON cifras repetidas que se acepta tal cual) y el cruce que fija la consistencia lector/escritor sobre una rejilla de vigentes × factores. Ese cruce se juzga sobre el número que el lector **devuelve**, no sobre el que propuso la IA: al revés comparaba el veredicto del corregido contra el juicio del crudo.

### Rendimiento km/gal · el techo, la mediana y el motivo (`lib/rendimiento.ts`)

La fórmula estaba escrita **cinco veces**, con tres umbrales y dos criterios de promedio: `app/combustible/page.tsx`, `lib/radar/acciones.ts`, `lib/odometro-analitica.ts`, `lib/elia/herramientas.ts` y `lib/costeo-servicio.ts`. La única que descartaba lo absurdo y usaba mediana era la última — la que decide el **margen de los servicios**. Las otras cuatro publicaban el disparate.

**El caso real** (CWZ-371, diésel): entre el 16/07 y el 05/08/2026 no hay ninguna carga registrada, así que la del 05/08 se comió 1 592 km acumulados y los dividió entre sus 9.77 galones → **162.9 km/gal**. Se pintó **verde con ✓** porque el color solo miraba hacia abajo (`rend < promedio * 0.7`, sin cota superior). Después entró en la media, la subió de 28.61 a 43.53 y colocó el umbral en 30.47 — justo por encima del rendimiento real de la unidad (27.2 a 30.6). Resultado medido: **siete de nueve filas sanas en rojo y la única rota absuelta.** Un panel que hace eso enseña a ignorar los rojos, que es lo único que no se puede permitir.

- **LA CADENA VA POR FECHA, NO POR KILOMETRAJE.** Ordenar por el valor que se está midiendo es circular: el km malo se *acomoda* en vez de delatarse. Con el dígito de más que este ERP ya conoce (`RATIO_DIGITO_DE_MAS`, `lib/odometro.ts`), un `1754450` tecleado por `175445` se va al final de la cadena y **re-enlaza todas las cargas posteriores con el predecesor equivocado**: una fila mala contamina N tramos y los N salen con pinta razonable. Por fecha se rompen exactamente **dos**, y en la fila donde está el error, que es donde alguien lo arregla. Desempate intradía por kilometraje; **nunca por `created_at`**, que es hora de inserción y no del hecho.
- **HAY DOS TECHOS Y HACEN TRABAJOS DISTINTOS.** El de **familia** (`TECHO_FAMILIA`, constante) **descalifica**: lo que lo supera no es una medición. El **derivado** de la propia unidad (`3 × mediana`) solo **juzga**. El constante es lo único que funciona con dos cargas y ningún historial —cuando la mediana de un solo valor *es* el outlier— y lo único que puede bloquear al Radar sin bloquear por "raro". El de galones es **heredado literal** del 40 de `costeo-servicio.ts`, no reelegido; el de GNV (12 km/m³) es el que demuestra que una constante única estaba mal: con el 40, un tramo de GNV tendría que estar **cuatro veces** equivocado para que alguien se enterara.
- **`KM_DIA_MAX` SEPARA "FALTAN CARGAS" DE "ESTE KM ESTÁ MAL", y el rendimiento solo no los distingue.** 1 592 km en 20 días son 80 km/día: el odómetro está bien y lo que falta son cargas → la lectura sirve de base para el tramo siguiente. 1 579 450 km en 4 días es imposible: el odómetro está mal → **no** sirve de base, o el error se propaga. Es el mismo 1500 de `registrarLectura` y `config_mantenimiento.km_dia_max`, no un umbral nuevo.
- **EL MOTIVO SE DECLARA, NO SE OLFATEA.** Nueve códigos (`MotivoSinRendimiento`) donde había un solo `—` que colapsaba cinco casos, cada uno con su arreglo en otro sitio. La pantalla enruta por código, igual que los bloqueos de `/liquidaciones`. Invariante que fija la matriz: **`rendimiento != null` XOR `motivo != null`**. El número descalificado viaja en `crudo` y **se muestra tachado**: un dato que se esconde obliga a ir a buscarlo a la base.
- **UN ESLABÓN SALTADO BLOQUEA EL NÚMERO.** Una carga con `kilometraje = 0` dentro del tramo significa que esos km se hicieron con combustible que **no está en el denominador**: el resultado sale inflado *por construcción*, no "quizás", y es detectable exacto. No publicarlo no es callarse — se dice cuántas cargas quedaron fuera, que convierte un `—` muerto en una tarea de diez segundos. **Rechazado a propósito**: sumar el combustible saltado al denominador. Es aritméticamente defendible pero cambia en silencio *qué mide la fila* y tapa un hueco que una persona puede cerrar.
- **LOS DOS HALLAZGOS SON DOS NEGOCIOS DISTINTOS.** `rendimiento_bajo` es plata que **se fue** (fuga, sifoneo, ruta pesada). `rendimiento_alto` es plata que **falta en los libros**: una carga comprada y consumida que no está en `v_egresos`, así que el costo de esa unidad está subvaluado y el margen de sus servicios, inflado. Un solo cubo era lo que hacía que el ERP se felicitara por un agujero en su propio registro.
- **La unidad importa**: el Radar guarda **litros** en la columna `galones` con `unidad: "litros"` y nadie lo miraba → un diésel en litros daba ×3.785 rotulado "km/gal". Se normaliza a la unidad de la familia; lo que no se sabe convertir sale como `unidad_desconocida` y no se adivina. `LITROS_POR_GALON` vive en `lib/combustible-tipos.ts`; **el literal de `lib/costeo-propio.ts` no se sustituye** (motor congelado que `prueba-costeo.mts` compara al sexto decimal).
- **En el Radar bloquea solo el techo CONSTANTE** (`fisico: true`), nunca la banda estadística: si no, la primera carga tras una parada legítima de un mes frenaría un voucher bueno, y un bloqueo que sale siempre se vuelve paisaje. Bloquea el físico porque ese km se escribe además en `lecturas_odometro` y envenena todos los tramos siguientes y el km de vencimiento de mantenimiento. `consumo_excesivo` **conserva su código** (hay filas históricas en `radar_combustible.anomalias` y `/radar-ia` filtra por él); el nuevo es `rendimiento_implausible`, dado de alta en `lib/radar/tipos.ts` **y** en `ANOMALIA_LABEL` de `app/radar-ia/page.tsx` — un código sin etiqueta imprime el código crudo.
- **El CPK de `/combustible` era `costo del período ÷ vehiculos.kilometraje_actual`**: el gasto de unas semanas dividido entre el odómetro de **toda la vida** del vehículo, y encima pintado de verde por ser pequeño. Ahora es soles y km **de las mismas filas medidas**, publicado con su cobertura, y sin tramos medidos sale `—`. El CPK contra el odómetro real **no se calcula ahí a propósito**: esa pantalla no tiene período (el filtro admite "todos"), así que el denominador honesto sería la historia entera de la flota; ese número ya existe y es la definición única del ERP en `/mantenimiento → Analítica de vehículo` (`indicadoresEconomicos.costoPorKm`).
- **La columna por conductor declara sus dos trampas**: un tramo tiene dos cargas y puede tener dos conductores (se atribuye al que **cierra**, y solo si ambos extremos traen el mismo nombre; si no, se cuenta aparte — aquí el número señala a una persona), y comparar conductor contra conductor no significa nada (quien maneja la van siempre le gana al del bus), así que se compara el **Δ % contra la mediana de la unidad que manejó**.
- **`lib/ayuda/modulos-flota.ts` se actualiza en el mismo commit.** Decía *"el ERP levanta la bandera 🚨 en dos casos, y solo en dos"* y describía el promedio: sin tocarla, la pantalla pasa a mentir sobre lo que hace el sistema.
- **UNA UNIDAD BICOMBUSTIBLE NO TIENE UN km/gal, TIENE DOS — Y NINGUNO SE PUEDE MEDIR EN UN TRAMO COMPARTIDO** (`familia_cruzada`, `MarcaOtraFamilia`, `cruzaElTramo`). La CWQ400 es una van a **GLP + gasolina**: GLP casi siempre, gasolina pocas veces (aire acondicionado, subidas, acelerones). Las cadenas se arman por `(unidad, familia)`, así que los km hechos con el OTRO combustible caen igual en el delta del odómetro y **no** están en el denominador. La cadena de gasolina se rompe de forma escandalosa: entre dos cargas de gasolina pasan semanas de GLP → cientos de km/gal → por encima del techo de 40 → `implausible`, que la pantalla titula **"Falta registrar una carga"** y que en el Radar **BLOQUEA el voucher**. Es un rojo falso que manda a buscar un repostaje que nunca faltó, y encima `rendimiento_alto` significa "plata que falta en los libros" — que aquí es sencillamente falso: el combustible SÍ está en los libros, en la cadena de al lado.
  - **Va ANTES de `implausible`**, por la misma razón que la inversión cantidad↔precio va antes de `precio_fuera_de_rango`: el techo superado es el **síntoma**.
  - **Es `eslabon_saltado` por otra puerta —el denominador incompleto— pero con código propio porque el arreglo es distinto**: el eslabón saltado se arregla poniendo el odómetro que falta; esto **no se arregla**, es cómo funciona la unidad. El detalle lo **desmiente explícitamente** ("no es una carga que falte registrar"), que es más fuerte que no mencionarlo: es justo la conclusión a la que llega solo quien ve un rendimiento imposible.
  - **Se DERIVA, no se guarda.** Ser bicombustible no es una columna de `vehiculos` que alguien deba mantener: `seriesRendimiento` es el único sitio que ve todas las familias de una unidad a la vez, y ahí se saca. El día que la CWQ400 deje de cargar gasolina, sus tramos vuelven a medirse sin que nadie toque una ficha. Misma regla que el `area` de caja chica.
  - **LOS ADITIVOS NO CUENTAN, y es lo que evita un falso positivo masivo**: la urea no mueve el bus, así que un camión diésel que carga AdBlue **no** es bicombustible. Contarla borraría el rendimiento de media flota.
  - **El intervalo es `[kmPrev, km)`**: el combustible de una carga se quema DESPUÉS de su lectura, así que la que coincide con la apertura se consumió dentro del tramo y la que coincide con el cierre ya es del siguiente. Sin odómetro se cae a la FECHA — sus galones movieron el bus igual, y no mirarla es el agujero por el que el tramo se publicaría inflado.
  - **`otrasFamilias` es opcional y omitirla deja el comportamiento intacto**, byte a byte (la matriz lo fija). Por eso `lib/costeo-servicio.ts` —que pre-filtra por familia y no las pasa— **no cambió**: mover el presupuesto de un servicio exige antes correr `diagnostico-rendimiento.mts` y revisar el diff placa por placa, que es la condición que este mismo documento le pone a ese archivo. **Queda pendiente, y con consecuencia conocida**: en una unidad bicombustible la mediana de la familia dominante está inflada por los km de la otra, así que el combustible presupuestado sale **por debajo** del real y el margen de sus servicios, por encima.
**La comparación del final del historial · el gasto sube por TRES causas y se gestionan al revés** (`compararVentanas` en `lib/rendimiento.ts` + `app/combustible/ComparacionPeriodo.tsx`). Poner km y gasto lado a lado no basta: **más km es más trabajo** (y más facturación), **peor rendimiento es la anomalía**, y **un precio más alto es del mercado**. El diésel pasó de S/ 24.70 (14/08) a S/ 25.74 (03/09) — **+4.2 % de gasto sin que nadie haya hecho nada mal**, que sin separarlo se lee como problema operativo, y un aviso que salta por algo que nadie puede arreglar se vuelve paisaje.

- **La diferencia de gasto se DESCOMPONE en soles**, variando un factor por vez sobre `gasto = km × (1/rendimiento) × precio`, en orden **volumen → eficiencia → precio**. Suman **exacto** `g₁ − g₀`; la matriz lo fija al céntimo. Es una descomposición **secuencial, no simétrica**: el residuo de interacción cae en el ÚLTIMO factor, y por eso el orden está declarado y no se reordena — el precio va al final porque es el efecto típicamente menor y el más exógeno.
- **El `total` del reparto es la diferencia REAL, no la suma de los tres.** Si la aritmética se desviara alguna vez, se vería en pantalla en vez de cuadrar sola.
- **Solo entran tramos MEDIDOS**, y `gastoTotal` se publica APARTE con todas las cargas: es el que cuadra con caja y con el KPI de arriba. Enseñar solo el medido haría que los dos números no cuadren y que el operador dude de ambos.
- **El filtro de mes MANDA sobre la ventana** (agosto vs julio; «todos» → 30 días vs los 30 anteriores). Una ficha que ignora un filtro visible en la misma pantalla es la forma más fácil de leer mal un número. El mes anterior es el mes **calendario**: restar días haría que el anterior de febrero fuese un trozo de enero.
- **El color NO es «sube malo» en todas las fichas.** Más km es **neutro**; menos rendimiento y más costo/km son rojos. Deducirlo del signo pintaría de rojo un mes en que se trabajó más.
- **Sin filtro de vehículo el agregado ESCONDE la anomalía**: con diez unidades, una que empeoró 25 % mueve el total un 2.5 %. Por eso debajo va la lista por unidad ordenada por cuánto se movió su rendimiento, peor primero — y las de pocos tramos al final y en gris, no entre las alarmas.
- **Cuando no se puede comparar, el motivo NOMBRA lo que sí hay.** «No hay tramos medidos» sobre un periodo con dos cargas y S/ 466.75 de gasto hace dudar de la pantalla: el operador ve cargas en la tabla y lee que no hay nada. El mensaje distingue *sin cargas* / *una sola carga* / *cargas sin odómetro*, y dice que poner el odómetro que falta hace aparecer la comparación. Nunca un −100 % ni un `Infinity`.
- **La columna KM son dos números**: el odómetro pequeño arriba y los km recorridos desde la carga anterior en grande, que es lo accionable. Sin odómetro sale `—` y **nunca `0`** — un cero se lee como «no recorrió».

- Matriz: `npx tsx scripts/prueba-rendimiento.mts` (trae el caso CWZ-371 dentro, el algoritmo viejo copiado literal para probar que reproduce el bug, y la sección que fija **el lado que no se puede aflojar**: un rendimiento alto legítimo no puede desaparecer). Medición sobre datos reales, solo lee: `npx tsx scripts/diagnostico-rendimiento.mts` — **correrlo y revisar el diff placa por placa es la condición para tocar `lib/costeo-servicio.ts`**, porque ese número entra al presupuesto de cada servicio.

### El rendimiento del parámetro se PROPONE, nunca se actualiza solo

`lib/costos/rendimiento-tipo.ts` (motor PURO) + `lib/costos/rendimiento-flota.ts` (el que lee) + la columna **Medido** de `/configuracion/costos → Flota / Vehículos` + `ModalRendimientoMedido.tsx`. Matriz: `npx tsx scripts/prueba-rendimiento-tipo.mts`. Medición sobre datos reales (solo lee): `npx tsx scripts/diagnostico-rendimiento-tipo.mts` — **correrlo y revisar tipo por tipo es la condición para APLICAR la primera propuesta**, no para fusionar. La diferencia con `lib/costeo-servicio.ts` es exactamente la que justifica todo este módulo: aquel cambiaba en silencio el número que usaba el presupuesto, así que había que medir el diff antes del merge; este no mueve ningún número hasta que alguien pulsa un botón, y hasta entonces lo único que hace es enseñar dos cifras juntas. Fusionarlo es lo que permite ver las propuestas; aplicarlas es lo que hay que ganarse con el diagnóstico.

**El caso**: el tipo `SPRINTER_17` llevaba **19.00 km/gal** tecleados mientras su única placa propia, la CWZ-371, medía **28.61** sobre once tramos sanos (el implausible que deja el hueco de registro ya queda fuera solo). El renglón de combustible de ese tipo estaba **50 % por encima del real en toda cotización nueva** — y el ERP ya sabía el número: lo pinta en `/combustible` desde que existe `lib/rendimiento.ts`.

**Y el desenlace es el argumento entero.** El dueño lo corrigió a mano, a mitad de este trabajo, yendo a `/combustible` a leer el 28.61 y volviendo a teclearlo en el parámetro. O sea: el dato no faltaba y el ERP no estaba equivocado — lo que faltaba era **ponerlos en la misma pantalla**. Un número que solo se alcanza copiándolo entre dos módulos se corrige el día que alguien se acuerda, y las diez categorías que nadie recuerda se quedan como nacieron. Por eso el remedio no fue un cron que escribiera el número, sino una columna que lo enseñe al lado del que se está usando: hoy ese tipo sale `ya coincide` y sin botón, que es exactamente lo que tiene que decir un parámetro que ya está bien.

- **NO SE APLICA SOLO, Y ESA ES LA DECISIÓN DE DISEÑO ENTERA.** Un cron que escriba `rendimiento_1` mueve el costo por km de una categoría y, como el margen es sobre el **precio** (`costo/(1−margen)`, ver `lib/costeo-propio.ts`), **abarata el precio ofertado de toda cotización nueva de ese tipo** ~20 %. La asimetría es la de siempre: un costo inflado se discute antes de vender; uno corto se descubre cuando el servicio ya se prestó. El ERP propone con la evidencia delante y firma una persona.
- **Son DOS IDENTIDADES unidas por texto libre.** El rendimiento se MIDE por `(placa, familia de combustible)` sobre `combustible`; se COSTEA por `parametros_costos.tipo_vehiculo`. El puente es `vehiculos.tipo_vehiculo_costeo`: texto, nullable y **sin FK**. Las siete reglas para convertir una en otra están declaradas en el módulo puro para que no aparezca una octava dentro de una pantalla.
- **La familia del parámetro sale de un mapa EXPLÍCITO** (`familiaDeParametro`), nunca de `familiaCombustible()`, que **cae a diésel ante cualquier valor desconocido**. El `<select>` de esa pantalla se llena de `precios_combustible.tipo`: basta con dar de alta un `"Gasohol 90"` para que ese tipo reporte familia diésel y se le ofrezca la mediana de otra unidad. Sin coincidencia: `familia_desconocida`, y no se propone nada.
- **SOLO VOTAN LAS UNIDADES PROPIAS.** `vehiculos_tercero.tipo_vehiculo_costeo` apunta a **las mismas filas** de `parametros_costos` —no hay espacio de nombres— y a un tercero se le paga por factura, no por kilómetro: su conductor y su mantenimiento no son de AFA. Se MUESTRAN (y se nombran como quien **hereda** el número), no mueven la mediana.
- **Una placa, un voto: mediana de MEDIANAS, no del pool de tramos.** Agrupar tramos le daría triple peso a la unidad que reposta el triple, y el tipo terminaría siendo "el rendimiento de la unidad que más carga". Una unidad **bicombustible** llega con dos series (`(unidad, familia)`) y se colapsa a una antes de contar: sin eso saldría dos veces en la pantalla y contaría dos votos.
- **Se propone la MENOR entre el historial completo y los últimos 90 días.** Asimétrico del lado seguro y sin ningún umbral: un motor que se degradó hace seis meses no puede colarse con una mediana que la unidad ya no hace. La ventana reciente se **filtra** sobre los tramos ya medidos, **nunca se re-serializa**: re-partir la cadena desde una fecha convertiría su primer tramo en `primera_carga` y perdería uno bueno cada vez.
- **EL GATE DE HALLAZGOS ES ASIMÉTRICO, Y NO POR DESCUIDO.** `rendimiento_alto` (no físico) **bloquea** la propuesta → `revisar_cargas`: es la firma de una carga comprada, consumida y no registrada, o sea plata que falta en los libros, y es el único modo de fallo que **infla la mediana sin dejar rastro** (no deja `sin_odometro` ni `eslabon_saltado`: deja la cadena cerrada y el denominador corto). `rendimiento_bajo` **no** bloquea: es costo real (mes pesado, ruta de cerro, sifoneo) y excluirlo sesgaría la mediana hacia arriba, o sea hacia el error que no vuelve.
  - **El `implausible` NO cuenta en ese gate** (`juzgarTramo` lo devuelve con `fisico: true`). Ya está fuera de la mediana por construcción, y contarlo dejaría el caso que motivó la funcionalidad —la CWZ-371 con su 162.9— bloqueado para siempre en `revisar_cargas`. Sí se **enseña tachado**, con su número crudo: un dato que se esconde obliga a ir a buscarlo a la base.
- **El motivo se DECLARA, no se olfatea**: doce códigos (`CodigoAgregado`), cada uno con su arreglo en otro sitio, y la pantalla enruta por código igual que los bloqueos de `/liquidaciones`. Dos invariantes que fija la matriz por barrido: `proponible === (codigo === "medido")`, y hay número exactamente en los cinco códigos que lo tienen. `aportan` y `observadas` son **disjuntas y exhaustivas**: una placa que se ve en la flota y no aparece en ninguna de las dos es una unidad que la pantalla no explica en ningún sitio.
- **CON DOS O MÁS VOTANTES NO SE PROPONE** (`varias_placas`): se enseñan las dos y decide una persona. **No hay umbral de dispersión y es deliberado**: con tres placas propias no hay muestra con la que calibrarlo, y este repo mide sus umbrales o los hereda literales — elegir uno y llamarlo herencia sería inventarlo. `PASO_RENDIMIENTO` (0.5) y `MIN_TRAMOS_CONFIABLE` (5) **sí** son heredados: el `step` del propio campo y el mínimo que ya usa `serieRendimiento`.
- **Un tipo BIMODAL no se propone nunca.** `rendimiento_1` significa "km por galón del combustible 1 **sobre los km hechos con el combustible 1**", y la mediana medida es Δodómetro ÷ galones de una familia: el odómetro no sabe de qué tanque salieron los km. Es la misma razón por la que `decidirRendimiento` (lib/costos/rendimiento-aplica.ts) tampoco lo sustituye en el presupuesto.
- **LA MEMORIA DE LA DECISIÓN SE DERIVA DEL HISTORIAL, sin columnas nuevas** (`procedenciaDeHistorial`). La adopción se reconoce por el prefijo `"Auto:"` del motivo, que compone `motivoHistorial` y **no la pantalla**: quien escribe y quien lee derivan la clave por el mismo camino, que es la regla que este repo pagó tres veces en un día. El descarte (`campo_modificado = "rendimiento_1_medido"`) **no escribe `parametros_costos`** —es un registro de decisión, no de cambio, y por eso `valor_anterior` va en null: poner ahí el tecleado pintaría en el historial una variación que no ocurrió—. Y el sello **CADUCA** si después cambia `tipo_combustible_1`: `cambiarComb` no toca `rendimiento_1`, así que un tipo que pasó de diésel a GLP conservaría una marca de "medido" sobre un km/gal de diésel.
- **No hay botón en la celda.** `CeldaEditable` guarda en `onBlur`: un botón pegado al lado invita al clic ciego sobre el único campo de esa pantalla que mueve dinero en dos módulos. El chip **abre** la evidencia (los dos números con etiquetas distintas, quién lo mide, qué se descartó, quién hereda, cuántos soles) y el botón vive dentro, con un `confirm()` que **nombra la plata** en vez de preguntar "¿estás seguro?". Y **nunca hay un «usar esta»** junto al número tecleado — mismo criterio que el PAX contratado de `/programacion` y el km vigente de `/radar-ia`.
- **La columna solo sale con la categoría ⛽ Combustible puesta**: es lo único que la flota mide, y una columna vacía en las otras cinco se leería como "aquí tampoco hay medición".
- **El cargador no mide nada por su cuenta**: siembra `seriesRendimiento`, el mismo motor de `/combustible` y del Radar. Dos motores que contestan la misma pregunta terminan contestando distinto — es literalmente el bug del semáforo de puntualidad. Lee `combustible` **paginado y filtra en memoria**, no con un `.in()`: una fila apunta a una de las dos flotas (`vehiculo_id` xor `vehiculo_tercero_id`), así que un solo `.in()` se dejaría la mitad en silencio. Y `cargarProcedencias` pide el historial **paginado**, no el `limit(150)` de la pantalla: con el corte, un tipo que no se toca hace meses perdería su sello en cuanto otros empujen sus filas fuera, y el chip volvería a proponer lo que ya se descartó.
- **Toda la columna es best-effort**: si falla, se queda vacía y el resto de la pantalla sigue sirviendo. Mientras carga dice *"midiendo…"* — **nunca se afirma un vacío mientras se está buscando** (mismo criterio que `estadoFotoRadar`).

### El mantenimiento por km se MIDE, y la edad de la flota delata la ficha que la deprecia

`lib/costos/mantenimiento-tipo.ts` (motor PURO) + `lib/costos/mantenimiento-flota.ts` (el que lee) + la columna **Medido** de `/configuracion/costos → Flota / Vehículos` con la categoría 🔧 Mantenimiento, la columna **Flota** con 📉 Depreciación, `ModalMantenimientoMedido.tsx` y `ModalAntiguedadTipo.tsx`. Matriz: `npx tsx scripts/prueba-mantenimiento-tipo.mts`. Medición sobre datos reales (solo lee): `npx tsx scripts/diagnostico-mantenimiento-tipo.mts` — **correrlo es la condición para APLICAR la primera propuesta**, no para fusionar: mientras nadie pulse el botón, esto no mueve ningún número.

**La pregunta que lo abrió**: *"la depreciación de 10 años vale para los buses premium; los que compramos con más de 10 años de antigüedad cuestan el 20-30 % de uno 0 km, ¿cómo configuro estándar y premium?"*. Y la primera respuesta es que en el cotizador **MÍNIMO/ESTÁNDAR/PREMIUM (15/20/25 %) son MÁRGENES, no clases de bus**: los tres salen del mismo `baseCosto` del mismo tipo, así que hoy "premium" significa *el mismo bus cobrado 5 puntos más caro*. La clase es un **TIPO** (`parametros_costos` + `vehiculos.tipo_vehiculo_costeo`), nunca un descuento sobre un renglón.

- **`mantenimiento_km` ERA EL ÚNICO RENGLÓN GRANDE QUE NADIE MEDÍA.** Se teclea una vez —1.20 S/km, el valor del alta (`FRM0`)— y ahí se queda para el bus de 2022 y para el de 2009, mientras la tabla `mantenimiento` guarda cada orden con su costo y su kilometraje desde el día uno. Es la misma historia del rendimiento medido y por eso este módulo es su espejo. Ojo: `indicadoresEconomicos.costoPorKm` (lib/odometro-analitica.ts) es el costo/km del **COMBUSTIBLE**, no el del taller — no hay ningún otro sitio que calcule esto, así que el motor nace en el módulo puro y el cargador solo le entrega filas.
- **Y ES EL RENGLÓN QUE DECIDE SI LA ESTÁNDAR SALE MÁS BARATA.** Con los números reales de AFA (Bus 50 pax, depreciación S/ 77.73 en 106 km = 0.73 S/km), una unidad usada ahorra ~0.43 S/km de capital y un mantenimiento 0.70 S/km más caro **se lo come entero**. Bajar solo la depreciación hace que el ERP oferte por debajo de su costo — la sección 6 de la matriz lo fija con el motor de costo por km de verdad: la estándar "honesta" sale **18.7 % por encima** de la que solo tocó el capital.
- **AQUÍ NO SE USA LA MEDIANA, SE USA LA TASA (Σ soles ÷ Σ km), y es la decisión que más fácil se "arregla" por parecido con el módulo gemelo.** El mantenimiento es a tirones: la mediana de los tramos descartaría la reparación mayor —un costo REAL que ocurre cada tantos miles de km— y publicaría el de los meses tranquilos. Eso es equivocarse hacia ABAJO, el error que no vuelve. En el combustible la mediana es la correcta por lo contrario: ahí el outlier es un hueco de registro, no un gasto.
- **NO HAY VENTANA RECIENTE QUE DECIDA.** El espejo del "se propone la MENOR de las dos ventanas" sería proponer la MAYOR, y sería un error: una reparación mayor dentro de los 90 días la convierte en una tasa que la unidad no hace todos los meses y dejaría la categoría fuera de mercado. La ventana se **ENSEÑA** (`reciente`) y no mueve la propuesta.
- **EL NÚMERO ES UN PISO, NUNCA UN TECHO, y el módulo lo dice.** Solo cuenta lo asentado en `mantenimiento`: un repuesto pagado por caja chica que nadie convirtió en orden de trabajo no está. El modal publica cuántas órdenes quedaron fuera y por qué, en vez de afirmar "esto es lo que cuesta mantenerla".
- **La cadena va por FECHA y el costo se atribuye al tramo que la orden CIERRA.** Es el espejo del `[kmPrev, km)` del combustible: el combustible se quema DESPUÉS de su lectura, el mantenimiento se paga DESPUÉS del desgaste que lo causó. Por eso la primera OT con kilometraje es cabecera y no aporta. Una OT **sin** kilometraje no rompe la cadena: su costo se acumula y lo recoge el primer tramo que cierre (la plata se gastó dentro de esos km igual, y dejarla fuera publicaría un mantenimiento más barato que el real). Un odómetro que retrocede o que salta por encima de `KM_DIA_MAX` descarta su tramo y **re-ancla** en la lectura nueva. Anuladas fuera (plata que nunca salió) y programadas a futuro fuera (no han ocurrido, y sus km tampoco).
- **EL NEUMÁTICO YA SE COBRA EN OTRO RENGLÓN, así que se NOMBRA y no se descuenta solo.** `parametros_costos` cobra las llantas aparte (`n_neumaticos × costo_neumatico / vida_neumatico_km`), de modo que una compra registrada como OT entraría dos veces. Detectar por texto es adivinar, y **adivinar de más es lo caro**: una OT que solo menciona una llanta quedaría fuera y el costo saldría por debajo del real. Por eso las filas se cuentan igual, el tipo sale `revisar_neumaticos` **sin botón** y la pantalla enseña las dos cifras. "Alineamiento" y "balanceo" **no** están en la lista: son servicio, no compra.
- **El motivo se DECLARA, no se olfatea**: diez códigos (`CodigoMant`), cada uno con su arreglo en otro sitio. Dos invariantes que fija la matriz: `proponible === (codigo === "medido")` y hay número exactamente en los **seis** que lo tienen. `aportan` y `observadas` son disjuntas y exhaustivas.
- **`pocos_registros` SÍ trae número, a diferencia de su gemelo.** El mantenimiento se registra a tirones, así que esconderlo dejaría la columna vacía en toda la flota — y una columna vacía se lee como "aquí no hay nada que medir", que es lo contrario de lo que pasa. Se enseña y no se propone.
- **Solo votan las propias**, y aquí la razón es más dura que en el rendimiento: a un tercero no se le paga el mantenimiento, se le paga una factura — `mantenimiento` ni siquiera tiene `vehiculo_tercero_id`. Se muestran como quien **hereda**.
- **La procedencia NO reutiliza `procedenciaDeHistorial`**: aquella CADUCA su sello al cambiar `tipo_combustible_1` (un km/gal de diésel no describe una unidad que pasó a GLP). Aquí no hay ningún campo que invalide la medición, y heredar esa caducidad borraría sellos sin motivo. `CAMPO_DESCARTE_MANT = "mantenimiento_km_medido"`.
- **La procedencia de los DOS parámetros se lee en UNA consulta** (`cargarProcedenciasCostos`): es la misma tabla y el mismo recorrido, y cada derivador ignora los campos que no son suyos.
- **LA EDAD DE LA FLOTA ES LA OTRA MITAD** (`cotejarAntiguedadTipo`, columna **Flota** de 📉 Depreciación). No mide nada nuevo: cruza `vehiculos.anio` con la vida útil que declara la propia ficha, igual que `cotejarFichaConTanques` cruza dos campos del mismo formulario. **El umbral no se inventa** — es esa vida útil: dos unidades separadas por una vida útil entera (2009 y 2022 con vida 10) es `mezcla`, una unidad cuya edad la supera es `supera_vida`, y con vida útil 15 la misma flota ya es `coherente`. Solo esos dos códigos pintan ámbar; `coherente` y `sin_placas` no pintan nada y `sin_anio` **no afirma que la ficha esté mal** (no hay con qué comparar). **No escribe nada**: lo que hay que hacer —duplicar la categoría y reasignar placas— son dos acciones en dos pantallas, y lo que faltaba no era un clic sino la evidencia.
- **La columna solo sale en las tres categorías que la flota sabe medir** (⛽ Combustible, 🔧 Mantenimiento, 📉 Depreciación). En las otras no se pinta: una columna vacía se leería como "aquí tampoco hay medición", que es distinto de "esto no se mide". Y toda la columna es **best-effort**: si falla, se queda vacía y el resto de la pantalla sigue sirviendo; mientras carga dice *"midiendo…"*, nunca se afirma un vacío mientras se está buscando.

**Las categorías estándar de arranque** (`supabase/costos-02-categorias-estandar-usado.sql`, **no la corre el deploy**): renombra las fichas actuales a `· Premium (0 km)` —solo el nombre, la CLAVE nunca— y clona cada una como `<CLAVE>_ESTANDAR` con factores **REFERENCIALES de mercado peruano**, pensados para editarse: `valor_compra × 0.25` (rango 20-30 % declarado por AFA; contraste NeoAuto set-2026, King Long urbano 9 m 2014 con 267 000 km en US$ 28 000), `vida_util_anios = 5` (la que QUEDA; coincide con el tope tributario de 20 %/año del art. 22 del Reglamento de la LIR), `residual_pct = 0.30` **sobre lo pagado** (la unidad ya sufrió la caída fuerte de la curva: una Coaster 1994 sigue ofertada en US$ 40 000), `mantenimiento_km × 1.60` (**el más incierto, y el que la columna Medido está para corregir**), `rendimiento_1 × 0.90`, `seguro_anual × 0.50` (la prima es sobre el valor asegurado), `vida_neumatico_km × 0.90`, y `euronorm = 'Euro III'` con `usa_urea = false` **forzados** — clonar la norma de la premium le cargaría AdBlue a un motor que no lo consume. `km_anio`, SOAT, revisión, permisos y `conductor_dia` **no cambian**: dependen del uso, no del año. **No reasigna placas**: eso se hace unidad por unidad en `/vehiculos`, que es donde alguien sabe si se compró nueva o usada; un UPDATE masivo por año adivinaría, y adivinar ahí mueve el precio de venta.

### «Premium» significaba DOS cosas, y el usado no puede salir más caro por un factor inventado

`lib/costos/equilibrio-usado.ts` (motor PURO) + los tres cuadros del cotizador + el comparativo emparejado + el bloque «Contra su gemela Full Equipo» de `ModalMantenimientoMedido`. Matriz: `npx tsx scripts/prueba-equilibrio-usado.mts`. Aplicación sobre datos reales (solo LEE, imprime el SQL): `npx tsx scripts/equilibrio-usado.mts`. Migración de nombres: `supabase/costos-03-nombres-por-antiguedad.sql`.

**Los dos defectos que reportó el dueño el día que vio las categorías nuevas en pantalla**, y son el mismo problema por dos puertas:

1. *"El premium debería ser más caro y sale más barato"* — las trece usadas costaban más que sus gemelas (Bus 50 a S/ 1 537 contra S/ 1 390). Medido sobre la Sprinter 17 a 106 km: de los **S/ 75** de diferencia, **S/ 54 eran el `mantenimiento_km × 1.60` que puso `costos-02` sin ningún respaldo**, S/ 10 el combustible, y la depreciación solo devolvía S/ 12.
2. *"Salen precio ESTÁNDAR y PREMIUM cuando ya elegí un bus premium"* — los tres cuadros del cotizador se llamaban igual que las fichas. **Son dos ejes y tenían el mismo nombre: la UNIDAD decide el COSTO, el MARGEN decide el PRECIO.**

- **LOS DOS EJES SE SEPARAN POR EL NOMBRE.** Las fichas pasan a `· Full Equipo (<10 años)` y `· Estándar (>10 años)` (`costos-03`, renombradas por `costos-05`): el paréntesis **no es decoración** — 10 años es el mismo umbral con el que la columna **Flota** de 📉 Depreciación avisa que una categoría mezcla unidades nuevas y usadas, así que el nombre dice el criterio con el que se decide a qué ficha va una placa. Los cuadros del cotizador pasan a `⛔ Margen mínimo (15%)` · `✅ Margen objetivo (20%)` · `⭐ Margen alto (25%)`, en los dos modos (eventual y fijo) — y la palabra «Estándar» puede volver a la ficha justamente porque los cuadros ya no la usan. **Solo cambia el NOMBRE: la clave `_ESTANDAR` no se renombra jamás** (es el puente sin FK con `vehiculos.tipo_vehiculo_costeo` y `cotizaciones.tipo_vehiculo`), y `emparejarFlota` empareja por la CLAVE, nunca por el nombre, que es texto editable desde el modal de ficha.
- **NO SE ELIGE UN FACTOR MEJOR: SE DEJA DE AFIRMAR.** Poner el mantenimiento de la usada igual al de la nueva diría que un bus de doce años mantiene como uno de fábrica —subestimar el costo, el error que solo se descubre cuando el servicio ya se prestó— y dejar el ×1.60 afirma lo contrario sin haberlo medido. El **punto de equilibrio** es el mantenimiento al que las dos fichas cuestan lo MISMO por km: por encima la usada cuesta más, por debajo menos, y en él el ERP no inclina la balanza. Su consecuencia se dice en pantalla: **con el equilibrio puesto, premium y usado cuestan igual y el premium se vende más caro POR EL MARGEN, no por el costo.**
- **Es un DESPEJE de la fórmula única, no una fórmula nueva**: se le pide a `componentesCostoKm` todo lo que la usada gasta sin el taller y se resta del costo total de la premium. Por eso **no se puede escribir en SQL** —sería la cuarta copia de la misma cuenta, la que `costo-km-parametro.ts` vino a matar— y por eso `scripts/equilibrio-usado.mts` calcula en TS e **imprime** el `UPDATE` de literales para que lo revise una persona, en vez de escribirlo.
- **Se redondea HACIA ARRIBA al céntimo**, y no es presentación: por debajo del equilibrio el ERP estaría afirmando que la unidad usada es más barata, que es justo lo que no se puede afirmar sin medir. Medio céntimo del lado caro no le mueve el precio a nadie.
- **El equilibrio NO tiene botón, y es deliberado.** El número que manda es el **medido**; un botón invitaría a pisar una medición real con un valor neutro de arranque. El bloque del modal lo enseña con los seis renglones al lado (la usada ahorra en depreciación y seguros, gasta más en taller, combustible y neumáticos) y dice de qué lado está hoy la ficha.
- **Su motivo en el historial NO lleva el prefijo `"Auto:"`** — ese es el sello de una medición adoptada (`motivoHistorialMant`), y si lo llevara, `procedenciaMantDeHistorial` marcaría la ficha como medida y el chip dejaría de proponer el número real el día que exista. La matriz cierra ese ciclo: escribe el motivo, lo lee de vuelta y comprueba que la procedencia sale `manual`.
- **Cuando no hay número, se NOMBRA**: `sin_gemela` (no es una usada, o su premium se desactivó), `parametro_incompleto` (un divisor en cero deja la cuenta en `Infinity` — no se convierte en un número), e `imposible` (ni con el taller en S/ 0.00 empata: lo que hay que revisar es el valor de compra, la vida útil o el rendimiento, y el detalle lo dice). Un cero o un negativo colados en el campo de mantenimiento serían dinero escrito al azar.
- **El comparativo del cotizador empareja**: cada Estándar va pegada a su Premium con el Δ de precio, no suelta cinco filas más abajo en el orden por capacidad — con las dos separadas, que una cueste más que la otra se lee como un fallo de la pantalla. El Δ va **sin color**: una unidad vieja más cara no es una alarma ni una más barata un logro, es el reparto entre capital y taller, y el color lo convertiría en juicio.
- **`emparejarFlota` no puede perder una ficha**: una usada huérfana (su premium desactivada) sale como fila propia. Una ficha activa que la pantalla no lista es una ficha que se sigue cotizando y que nadie ve — la matriz lo fija contando que todas aparecen exactamente una vez.
- **El hallazgo de negocio que deja medido este módulo**: el ahorro de capital de una unidad usada compra **muy poco** taller. Medido sobre los parámetros reales de AFA, el equilibrio cae entre **×1.16 y ×1.25** del mantenimiento de la gemela nueva (mediana ×1.20): Bus 50 → 2.39 contra 2.00; Sprinter 17 → 0.95 contra 0.85. O sea: **comprar usado no abarata el kilómetro, abarata la caja.**

**EL ESTADO EN QUE QUEDÓ, Y ES UNA DECISIÓN DEL DUEÑO, NO UN DESCUIDO** (`supabase/costos-04-estandar-provisional.sql`, **no la corre el deploy**). Con el ×1.60 puesto, la Estándar seguía cotizando más cara que la Premium en pantalla, y el dueño decidió —explícitamente y con la evidencia delante— **igualar los dos parámetros de forma provisional hasta tener datos reales**: `vida_util_anios` de la Estándar vuelve a los 10 años de su gemela y `mantenimiento_km` se copia del de la Premium. Con eso la Estándar sale **6-12 % más barata**, que es lo que el dueño espera ver.

- **Lo que eso AFIRMA, y está escrito en el acta**: que una unidad de más de 10 años mantiene igual que una de fábrica. Si gasta un 30-50 % más de taller, el S/km de la Estándar queda 8-15 % corto — un costo corto no se discute antes de vender, se descubre cuando el servicio ya se prestó. Se acepta con dos condiciones que lo hacen reversible: el acta dice **PROVISIONAL** con su fecha, y la columna **Medido** sigue proponiendo el número real en cuanto haya órdenes de trabajo con kilometraje.
- **La vida útil de gestión son los años que se espera SERVIR, no el tope fiscal.** `costos-02` había puesto 5 (la vida restante, alineada con el 20 % anual del art. 22 del Reglamento de la LIR); si un bus comprado a los 12 años va a trabajar 10 más, repartir su capital en 5 sobre-recupera y encarece cada kilómetro. **Los factores de `costos-02` para estos dos campos quedan superados por `costos-04`** — el resto (valor de compra ×0.25, residual, seguro ×0.50, rendimiento ×0.90, Euro III sin urea) sigue vigente.
- **Pendiente conocido, sin mezclar decisiones**: con vida útil de 10 años, el `residual_pct = 0.30` describe una unidad de 22 años valiendo el 30 % de lo que se pagó a los 12. Si resulta alto, bajarlo sube la depreciación ~0.03 S/km en un bus; es un ajuste de celda.
- **El script del equilibrio es el termómetro de esta decisión**: después de `costos-04` las Estándar quedan POR DEBAJO del equilibrio, y tanto él como el modal lo dicen con esas palabras. La afirmación que hace el ERP es medible en cualquier momento.

### El costo de una OT se CONGELABA, y la factura del taller no tenía dónde entrar

`lib/mantenimiento/costo-ot.ts` (motor PURO) + `lib/mantenimiento/ot-factura.ts` (el que lee y escribe) + `OrdenesTab.tsx`. Matriz: `npx tsx scripts/prueba-costo-ot.mts`. Migración: `supabase/mantenimiento-05-costo-factura-cxp.sql` (**no la corre el deploy**).

**Lo reportado fue «no existe dónde registrar el precio», y el campo existía** — el defecto es peor. `ordenes_trabajo.costo_total` no lo lee nadie fuera de su pantalla; quien cuenta el dinero es **`mantenimiento.costo`** (`v_egresos` lo publica, `v_costo_servicio` lo cruza y con él se mide el S/km de cada categoría). La copia entre los dos ocurría **una sola vez, al cerrar la OT**: una OT automática nace en 0 y se cierra en 0, así que su fila queda en cero **para siempre** y teclear el costo después no movía nada — «COSTO TOTAL S/ 0.00» con dos OT cerradas.

Lo que no cumple las tres se queda sin ancla y **la pantalla lo dice**.

Lo que de verdad faltaba es el lado FISCAL: la factura del taller como `documentos_compra`, que se aprueba, entra a un lote de pago, se concilia con el banco y sustenta el crédito fiscal. **`mantenimiento.documento_compra_id` ya existía desde la fase 06 y `v_egresos` ya lo publicaba — ninguna pantalla lo escribía.** Y no duplica: el propio `v_egresos` declara que «documentos_compra se suma aparte».

Sin eso la misma factura entraría dos veces —una por Contabilidad, otra desde la OT— y el índice único haría reventar la segunda con un error que no dice nada. `llaveFiscal` normaliza RUC, serie y ceros a la izquierda en **un solo sitio**: dos derivaciones distintas de la misma clave es el bug de siempre.
- **UN SOLO TOTAL, CON SU ORIGEN DECLARADO** (`totalDeOT` → `items` · `tecleado` · `sin_dato`). El PDF impreso llevaba desde siempre un `Costo: S/ ______` al lado de cada repuesto para rellenar a mano; ese es ahora un campo. - **EL IMPORTE DE LA FACTURA SE COTEJA, JAMÁS SE COPIA.** El total de la factura lleva IGV y el costo del taller va sin él —el IGV se recupera como crédito fiscal—, así que copiarlo mediría el S/km de la flota **18 % por encima** y subiría el precio de cada cotización de esa categoría. Por eso la diferencia de ~18 % tiene **código propio** (`difiere_igv`) en vez de salir como desacuerdo genérico: es el caso normal y no hay nada que corregir. Lo demás sale como `discrepa`, y decide una persona.

Insertar una nueva cuando falta el FK duplicaría un egreso ya asentado: el error caro, y en la dirección que no vuelve. Invariante de la matriz por barrido: **solo se escribe con OT cerrada Y ancla Y fila a la vista**. Una OT **abierta tampoco asienta**: el dinero se asienta cuando el servicio se hizo, misma razón por la que un presupuesto nunca va a `reservas.costo_proveedor`.

- **La migración no pisa un importe que ya dice algo**: solo escribe donde la fila está en 0 o null. Un costo corregido a mano en `/mantenimiento → Historial` es el número bueno.
- Todo lo que toca las columnas nuevas **reintenta sin ellas y lo AVISA nombrando el SQL**: que falte una migración accesoria no puede impedir abrir una orden de trabajo, pero un costo que parece guardarse y no llega al egreso sí hay que decirlo.

### Una OT la pagan VARIOS bolsillos, y uno de ellos no es un bolsillo

`lib/mantenimiento/lineas-costo.ts` (motor PURO) + `ot-factura.ts` (el que lee y escribe) + el desglose de `OrdenesTab.tsx`. Matriz: `npx tsx scripts/prueba-lineas-costo.mts`. Migración: `supabase/mantenimiento-06-lineas-de-costo.sql` (**no la corre el deploy**).

**Lo preguntó el dueño y era la mitad que faltaba**: *«¿qué pasa si los materiales los compramos aparte y la mano de obra en un taller tercero? ¿Y a futuro, cuando tenga mi mecánico y solo compremos el material?»*. La OT tenía UN costo y UNA factura, o sea describía solo el caso «todo al mismo taller». Un renglón es ahora una **línea** con cuatro datos que no se deducen: `tipo` (material · mano_obra · servicio), `origen`, `proveedor_id` y `documento_compra_id`, y las que hagan falta por orden.

- **`origen` NO ES UNA ETIQUETA: DECIDE SI EL SOL ENTRA A `v_egresos`.** La pregunta exacta que contesta es **¿salió plata de la caja POR ESTA ORDEN?** `comprado` → sí, suma a `mantenimiento.costo`, que es lo que `v_egresos` publica. `propio` → no: la hora del mecánico de planilla ya la pagó la planilla y el repuesto de almacén ya se pagó al comprarlo, así que contarlo sería el mismo sol dos veces —lo que evita `promoverGastos` filtrando `gasto_id is null`—. `origen` no pregunta QUÉ es: un material de almacén es `propio` igual.

Sin esa suma, el día que AFA contrate un mecánico el S/km medido BAJARÍA sin que el costo real hubiera bajado —solo se mudó a la planilla—, la columna «Medido» propondría ese número y el precio ofertado de la categoría bajaría con él. - **LA UNIÓN `líneas ∪ {ítems sin línea}` ES LO QUE IMPIDE PERDER DINERO.** La cascada natural («si hay líneas, mandan las líneas») BORRARÍA en silencio los costos ya tecleados en el checklist: S/ 200 en un ítem, una línea de mano de obra de S/ 150 después, y el total pasa de 200 a 150. Una línea anclada a un ítem (`checklist_ot_id`, con índice único parcial) lo SUSTITUYE y no se suma dos veces. **Sin líneas el reparto es byte a byte el anterior** —lo decide `totalDeOT` y todo es desembolso—, y la matriz lo fija sobre los cinco escenarios de `prueba-costo-ot.mts`.

Esa fila única de `config_mantenimiento` es hoy el **respaldo** — la tarifa que se usa cuando la línea no dice quién trabajó.

N° 1946-2009-MTC-15 · Tel: …` y el programa preventivo `AFA Tours Peru SAC`, literales en el TSX. **Este ERP se vende**: la OT de un comprador salía con el nombre —y con el número de habilitación— de otra empresa. Los dos resuelven ahora por `empresaConDefectos(perfil)`, el mismo escalón de la cotización y la liquidación.

Vacío significa vacío y el pie **omite la línea entera** en vez de inventarla. Misma regla que el PAX contratado y el km vigente: sin dato no se cae a otro número, se calla.

### El precio que se DECIDE es sin IGV; el que se GUARDA es con IGV

`app/cotizador/page.tsx` + `precioPaxSinIgv` en `lib/costeo-propio.ts`. Los tres cuadros de margen imprimían el importe **con IGV** en grande y el sin IGV en una línea gris de 11 px, y el comparativo de flota entero (Total 20 % · S/pax · Mín 15 % · Mes ×26) iba con IGV sin decirlo en ninguna cabecera. - **El IGV no es de AFA**: se cobra, se retiene un rato y se le entrega a SUNAT. Lo que se negocia, lo que sostiene el margen (`costo/(1−margen)` se calcula **antes** del IGV) y lo único comparable contra un competidor —que cotiza sin IGV— es la base imponible. Con el número bruto arriba, ese 18 % se lee como precio propio y toda comparación sale 18 % desviada.
- **LOS DOS SIGUEN A LA VISTA.** No se escondió el con IGV: es el que el cliente paga y el que va en la factura. Lo que cambió es cuál se lee primero.
- **El bloque «→ Enviar a Cotizaciones» SIGUE en con IGV, y sus etiquetas lo dicen** (`Total c/IGV`, `Precio/día c/IGV`). No es una incoherencia: es el importe que se **escribe** en `cotizaciones.precio_cliente` / `precio_dia`, que en todo el ERP es con IGV. Enseñar ahí el sin IGV para que "cuadre" con los cuadros de arriba haría que el número visible y el guardado fueran distintos, que es el error caro de esta pantalla — leer dos bases rotuladas no lo es.
- **El por-pax se DERIVA en el motor, no en la pantalla** (`precioPaxSinIgv`, aditivo — `prueba-costeo.mts` compara `precioPax` sin tocar y sigue en verde al sexto decimal). Dejarlo con IGV mientras el total de al lado va sin él pone dos bases en la misma tarjeta, que es lo que nadie detecta mirando. De paso muere el `precioPax20/1.18` hardcodeado de `app/cotizaciones/page.tsx`, que era una tercera definición del mismo asiento.
- **El Δ del comparativo se calcula sobre `sinIGV20` en las dos puntas**: una diferencia entre dos números que la tabla ya no enseña no se puede verificar contra ella.

### El tanque es de la UNIDAD; el combustible de una carga sigue siendo del PRODUCTO

`lib/combustible-tipos.ts` (el catálogo, que ahora es también el dueño del tanque) + el bloque **Capacidad de tanque** de `/vehiculos` y `/tercerizadas` + `components/flota/AvisoFichaCombustible.tsx` + `cotejarFichaConTanques` (lib/costos/rendimiento-tipo.ts). Matriz: `npx tsx scripts/prueba-tanque.mts`.

**La pregunta que lo abrió fue "¿falta registrar el tipo de combustible de cada placa?", y la respuesta es NO** — ese campo es justo el que la regla de arriba prohíbe: si el ERP dedujera el combustible de una recarga de la ficha del bus, el día que una unidad con kit GLP cargue gasolina lo registraría como GLP, con el precio de referencia equivocado. Lo que la unidad SÍ declara es **qué puede cargar y cuánto le entra**: `capacidad_tanque`, un jsonb por familia. Es estrictamente más informativo que un tipo único —una bicombustible declara dos— y **no afirma qué se despachó en ningún voucher concreto**, que es la línea que no se cruza.

- **SE ESCRIBÍA POR FAMILIA Y SE LEÍA POR TIPO.** El formulario guarda `{diesel: 100, gasolina: 80}` (familias) y los dos lectores —`getCapacidad` de `/combustible` y `capacidadTanque` de `lib/radar/acciones.ts`, la misma función copiada— buscaban con el TIPO leído del voucher. Con `diesel`, `glp`, `gnv` y `urea` la familia y el tipo se escriben igual y nadie lo notó; con `gasolina_regular` y `gasolina_premium` **la capacidad configurada no se encontraba nunca**. Es el patrón de *"escribir con una identidad y leer con otra"* por cuarta vez, y por eso la resolución vive ahora en `capacidadTanqueDe`, en un solo sitio.
- **Y al no encontrar la clave, remataba en `v.diesel`**: una carga de gasolina en un bus se comparaba contra el tanque de DIÉSEL (100 gal en vez de 80). El fallback existía para no devolver `undefined` y acabó publicando el tanque de otro combustible.
- **`"MINIBUS".includes("BUS")` es `true`**, y BUS iba primero en la tabla: **todo minibús se juzgaba con el tanque de un bus**, así que 70 galones en un minibús no levantaban nada. Se resuelve por la clave **más larga**, que es la misma lección del match del grifo (*nunca "contiene" a secas*).
- **`vehiculos_tercero.capacidad_tanque` EXISTÍA Y NO TENÍA PANTALLA.** La migración la crea en las DOS tablas y los dos lectores la consultan para las dos flotas, pero `/tercerizadas` no tenía el campo: las cargas de una unidad de tercero se juzgaban siempre contra el estimado por categoría y no había forma de corregirlo desde ningún sitio. Una columna que existe, que se lee y que nadie puede llenar es el mismo defecto que `multiples_recargas_en_cluster` declarado y sin emitir.
- **LA COLUMNA SE MANDA SIEMPRE, incluso en null.** Antes se incluía solo si traía valor —para no romper si la migración accesoria no se había corrido— y eso dejaba un dato que **no se podía BORRAR**: al vaciar los campos el payload dejaba de llevarla y la capacidad vieja seguía escrita, así que un 80 tecleado por error era corregible a otro número pero no retirable. La migración se protege **reintentando sin la columna que el error NOMBRA** (`faltaColumnaTanque`), que es el patrón de `COLUMNAS_OPCIONALES`, y se avisa en pantalla.
- **`FAMILIAS_TANQUE` se DERIVA del catálogo.** `/vehiculos` llevaba su propia lista de cinco filas escritas a mano y dejó de decir lo mismo el día que el catálogo abrió la gasolina por octanaje. `CAPACIDAD_TANQUE_CATEGORIA` también se mudó ahí: estaba copiada **literal** entre la página y el Radar, y la cabecera del catálogo ya lo confesaba sin que nadie la moviera.
- **EL DESPLEGABLE DE «CATEGORÍA DE COSTEO» AHORA DICE CON QUÉ COMBUSTIBLE COSTEA.** Mostraba `nombre (clave)` y nada más, y con eso se le asignó a una unidad de GLP una ficha que costea en otro combustible — algo que no se notó en ninguna pantalla hasta que el diagnóstico del rendimiento lo nombró meses después. Debajo, `cotejarFichaConTanques` cruza los DOS campos del **mismo formulario** y avisa en ámbar: el S/km es `precio ÷ rendimiento`, así que con el combustible equivocado el renglón se desvía en la razón entre dos precios —diésel y GLP van como 3 a 1—, no en un porcentaje.
  - **Cinco códigos, y solo dos se pintan en ámbar** (`discrepa`, `familia_desconocida`). `sin_tanques` es una línea gris que invita a llenar el bloque de arriba, y `coincide`/`sin_ficha` **no pintan nada**: el desplegable ya dice «— sin asignar —», y un aviso que sale siempre se vuelve paisaje.
  - **Sin tanques declarados NO se afirma que discrepe.** No hay con qué comparar, y el módulo prefiere callarse antes que inventar — la misma regla que el tri-estado del semáforo de puntualidad.
  - **Una bicombustible calza con cualquiera de sus dos familias**, sin preferencia: la ficha costea una y la unidad puede cargar las dos.
- **Lo que la matriz fija y no se puede aflojar**: diésel, GLP, GNV y urea dan un resultado **idéntico al del algoritmo viejo** sobre la rejilla entera (96 combinaciones, copiado literal en el script). Si eso cambiara, el arreglo habría movido el control de tanque de toda la flota de diésel sin que nadie lo pidiera. El MINIBUS es la única categoría que cambia, y a propósito.
- **Pendiente conocido, y no se inventó un número**: `SUV` y `CUSTER` son categorías que las dos pantallas ofrecen y que la tabla por categoría no tiene, así que caen al estimado por defecto (80 gal de diésel) — para una SUV eso es tan alto que el control no salta nunca. Se cierra declarando su tanque en la ficha de cada unidad, que es exacto; poner una fila estimada sería elegir un número sin medirlo.

### Costeo de la unidad propia (`lib/costeo-propio.ts`)

La fórmula del costo de mover un bus propio —combustible por km/galón con urea, neumáticos por vida útil, mantenimiento en S/km, depreciación, fijos anuales prorrateados, conductor por día, peajes, otros, más reserva 5 % y overhead 10 %— vivía **dentro** de `app/cotizador/page.tsx`, así que no la podía usar nadie más. Está extraída, y `calcular()` en el cotizador es ahora un adaptador que arma el `Resultado` con la forma que esa pantalla espera.

- **Se extrajo, no se reescribió.** `npx tsx scripts/prueba-costeo.mts` corre la versión original (copiada literal en el propio script) y la nueva sobre los mismos casos y compara al **sexto decimal**. Si algún día esa prueba falla, el motor cambió y todas las cotizaciones emitidas dejan de ser reproducibles.
- **El módulo no lee la base.** Recibe los parámetros resueltos y devuelve números; de dónde salen es cascada de quien tiene acceso a los datos, igual que `paxContratadoDe` en la liquidación.
- **Dos entradas mandan sobre `parametros_costos`** y declaran su fuente en `CostoUnidad.fuentes`: `costoConductorDia` (el costo EMPRESA real, con gratificaciones/CTS/EsSalud/SCTR según el régimen laboral) y `deprecKm` (la depreciación contable de esa placa, de `activos_fijos`). Un cero explícito es un dato, no la ausencia de uno — una unidad ya depreciada aporta 0.
- **Pernocte y viáticos entran DESPUÉS del overhead**: son reembolsos de bolsillo, no actividad que consuma estructura.
- **`precioConMargen` es sobre el PRECIO, no sobre el costo**: con 20 % el precio es `costo/0.8`, no `costo × 1.2`. Es la diferencia entre ganar 20 % y ganar 16.7 %.
- Todo divisor que venía de un parámetro sin llenar (`rendimiento_1`, `vida_neumatico_km`, `km_anio`) se protege: antes producía `Infinity`/`NaN` que se propagaba al precio.

### Presupuesto del servicio y utilidad antes de impuestos

`supabase/costeo-01-planilla-y-presupuesto.sql` + `lib/costeo-conductor.ts` + `lib/costeo-servicio.ts` + `components/programacion/ModalCostear.tsx`.

- **El estimado NUNCA va en `reservas.costo_proveedor`.** Tres razones duras: `v_costo_servicio` ya toma ese campo como costo del tercero cuando no hay factura **y además** suma los egresos reales (los mismos soles dos veces, contra la regla de oro); `fn_reservas_pacto_nacimiento` le pone `costo_estado='no_aplica'` a los propios —"no hay proveedor a quien pagarle"—; y cada cambio suyo levanta un acta `PSC-` contra un proveedor inexistente. El presupuesto vive en `servicio_costo_estimado` (+ líneas), versionado, con `parametros_json` congelado.
- **La fórmula del costo empresa vive SOLO en `lib/costeo-conductor.ts`.** En SQL, `v_conductor_planilla` publica los INSUMOS (sueldo, factores del régimen vigente, SCTR del período) y no calcula nada — si calculara, habría dos motores que discrepan. Mismo criterio que `lib/costeo-propio.ts`.
- **Los tres regímenes peruanos están cargados**, no el de AFA: `config_laboral_regimen` trae micro, pequeña y general con **fecha de vigencia**, y `config_laboral` dice cuál usa la empresa. El ERP puede venderse. Cambiar de régimen en noviembre NO debe mover los márgenes de agosto: por eso la vigencia. Factores: pequeña = grati 1 sueldo/año + CTS 0.5 (15 remuneraciones diarias) → **1.24× el básico**; general = grati 2 + CTS 1.1667 → **1.38×**. **AFP/ONP no entra: es descuento del trabajador**, y meterlo infla el costo ~13 %.
- **El VÍNCULO decide cómo se imputa** (`modoCostoConductor`), y no todos van por planilla: `planilla`/`plazo_fijo` → costo empresa prorrateado; `honorarios`/`eventual` → importe POR DÍA, completo, sin beneficios (se contratan para el servicio: pedirles un sueldo mensual inventaría una relación laboral que no existe); `service` → **no se imputa**, su costo ya está dentro de la factura del proveedor y contarlo sería cobrarlo dos veces.
- **El sueldo es del PERÍODO, no del servicio.** Se prorratea por días con servicio (de `v_conductor_dias_servicio`) y el día se **reparte** entre los servicios de esa jornada. Con honorarios no se prorratea nada: el importe del recibo es del servicio.
- **Se prefiere lo medido a lo parametrizado, PERO SOLO CUANDO SE PUEDE**, y cada dato declara su fuente: rendimiento real de la placa (**mediana**, no promedio — un tanque a medio llenar mueve la media) sobre `parametros_costos.rendimiento_1`; precio de la última carga sobre el de referencia; depreciación de `activos_fijos` (cuenta 6811) sobre la del parámetro. Sin fuente no se inventa: el renglón sale vacío y la pantalla dice por qué.
- **Quién gana entre lo medido y lo tecleado se decide en UN solo sitio: `decidirRendimiento` (lib/costos/rendimiento-aplica.ts), módulo PURO.** Antes la única condición era que coincidiera la familia del combustible, y detrás había tres agujeros. (1) **No miraba `resumen.confiable`**: `serieRendimiento` publica su mediana en cuanto hay UN tramo bueno, así que una unidad con dos cargas ya pisaba el parámetro del tipo en el presupuesto de cada uno de sus servicios — y una mediana de un solo valor ES ese valor. `juzgarTramo` ya exigía `confiable` antes de levantar un hallazgo; esto lleva el mismo guard al sitio donde el número se vuelve dinero. (2) **El `"km/gal"` estaba hardcodeado en las DOS ramas del renglón**, así que una unidad de GNV firmaba en galones un número en km/m³; la unidad sale ahora de `labelDeFamilia`, la misma que usa /combustible. (3) **Sustituía en los tipos BIMODALES**, y ahí se descuenta dos veces: `rendimiento_1` significa «km por galón del combustible 1 **sobre los km hechos con el combustible 1**», y la mediana medida es Δodómetro ÷ galones de la familia mayoritaria — el odómetro no sabe de qué tanque salieron los km, así que sale inflada ~`1/pct_uso_1` y la fórmula la vuelve a multiplicar por `pct_uso_1`. Con un 60/40 eso costea el combustible a la mitad.
  - **La asimetría que gobierna los tres**: en un presupuesto, equivocarse hacia ABAJO es lo caro. Un costo inflado se discute antes de vender; un costo corto se descubre cuando el servicio ya se prestó. Ante la duda manda el parámetro tecleado, que es una premisa que alguien firmó.
  - **El motivo se declara, no se olfatea** (`tipo_bimodal` · `sin_medicion` · `familia_distinta` · `pocos_tramos`), y cada uno se arregla en otro lado: `pocos_tramos` se cierra registrando cargas con odómetro, `familia_distinta` corrigiendo el combustible del tipo, `tipo_bimodal` no se cierra nunca. El renglón del presupuesto lo imprime; ninguna pantalla lo redacta.
  - Matriz: `npx tsx scripts/prueba-costos-parametros.mts` (sección 6, con la frontera exacta de `MIN_TRAMOS_CONFIABLE` y **el lado que no se puede aflojar**: una medición buena tiene que seguir mandando, o el cambio apagaría la funcionalidad sin que nadie lo note). La **condición de merge** es la sección 6 de `npx tsx scripts/diagnostico-rendimiento.mts`, que dice placa por placa qué rendimiento usaba el presupuesto ANTES y cuál usa AHORA, con el % que mueve el costo de combustible por km.
- **Lo que se amortiza no tiene columna «real»** (`cat_concepto_costo.amortiza`): neumáticos y depreciación no se gastan en un viaje. `v_utilidad_servicio` los publica como `costo_imputado`, separado del `costo_directo_real`, y marca `sin_presupuesto` — un servicio sin presupuesto muestra el imputado en cero y **parece dejar más de lo que deja**.
- **Al sumar conductor y desgaste, el margen de los propios BAJA.** No es un fallo: hasta ahora esos costos no se contaban.
- **La siembra de gastos previstos NO crea filas en `gastos`.** Sembrar el presupuesto ahí lo contaría como egreso real en `v_egresos`. Seguimiento lee `servicio_costo_estimado_linea` y solo ofrece rellenar el formulario.
- Pruebas: `npx tsx scripts/prueba-costeo.mts` (la extracción, al sexto decimal) y `npx tsx scripts/prueba-conductor.mts` (los tres regímenes, el prorrateo y los divisores en cero).

**LA INVERSIÓN CANTIDAD↔PRECIO QUE EL CUADRE NO PUEDE VER** (`detectarInversionCantidadPrecio`). La nota V87T-00008182 imprime `040002072 UGL 8.829x 6.990` con `GLP-G 61.71`: 8.829 galones a S/ 6.990. La IA guardó **6.99 gal a S/ 8.829** — y `6.99 × 8.829 = 61.71` cuadra exactamente igual, porque **la multiplicación es conmutativa**: ninguna cuenta con esos tres números distingue un caso del otro. Hace falta una CUARTA cifra de fuera del voucher, y es el **precio referencial del tipo** (`precios_combustible`, que AFA mantiene al día): con GLP a S/ 7.00, lo que quedó en "cantidad" (6.99) es el referencial casi exacto y lo que quedó en "precio" (8.829) se le va un 26 %. Esa asimetría es la firma.

- Se exige evidencia por los **dos** lados —el valor en `cantidad` pegado al referencial (≤ 8 %) **y** el de `precio` claramente fuera (> 20 %)—: el fallo caro es al revés, dar por invertida una compra legítima escribe un galonaje y un precio que nadie despachó. Sin referencial no se juzga.
- Va **antes** de `precio_fuera_de_rango`: con los números invertidos, ese aviso es el síntoma, no la causa.
- En el prompt, el ejemplo del GLP acompaña al del diésel a propósito: **no se decide por tamaño**. Con diésel el precio (24.640) es mayor que la cantidad (8.799); con GLP es al revés. Lo único que lo decide es la **"x"**, que va pegada a la cantidad.
- Matriz: `npx tsx scripts/prueba-combustible-tipos.mts` y los casos de inversión en `prueba-voucher.mts`.

**LA FOTO VIAJA CON LA CARGA HASTA `/combustible`** (`lib/radar/fotos-lectura.ts`). Todo lo de arriba —el cuadre, el grifo, la inversión, el álbum— termina en una fila de `combustible` con un número que a veces hay que enmendar, y esa pantalla no mostraba el papel por ningún lado: corregir era teclear de memoria justo el dígito que se leyó mal. Ahora el formulario **Editar carga** abre con la(s) foto(s) que la IA procesó y el nº de nota, las filas del historial que nacieron de una foto llevan **📷** al lado de la fecha, y la fila desplegada trae la misma tira.

- **El puente es `radar_combustible.combustible_id` y se lee AL REVÉS.** `combustible` no guarda nada del Radar (ni el id de la lectura, ni la foto, ni el comprobante), así que la única forma de saber qué papel originó una carga es preguntarle al Radar cuál carga escribió. Por eso la consulta es `.not("combustible_id","is",null)` y no un `.in()` con los ids de la pantalla: `combustible` se lista entero y esa URL reventaría.
- **La cascada de "qué foto leyó la IA" es compartida, no copiada**: `radar_combustible.fotos` (todas las del cluster) y, solo si está vacía —filas anteriores a `radar-ia-combustible-revision.sql`—, la media del mensaje de origen. `/radar-ia` la usaba inline; dos copias se desincronizan en la primera fila vieja, que es justo la que se audita. La media de respaldo se pide **al abrir la carga**, de a una: pedir todos los mensajes de golpe sería una URL kilométrica y una tabla entera para mostrar una miniatura.
- **`fotos` es de una migración accesoria**: si no se corrió, la consulta se reintenta sin esa columna. Ver la foto es un extra; que `/combustible` deje de listar cargas porque falta un SQL accesorio, no.
- **Nunca se afirma "no hay foto" mientras se está buscando** (`estadoFotoRadar`: `sin_radar | cargando | sin_foto | hay`), y un adjunto que no es imagen (el bucket guarda PDFs y audios) sale como enlace y no como un `<img>` roto, que se lee igual que "no hay foto".
- Matriz: `npx tsx scripts/prueba-fotos-lectura.mts`.

**La lista de grupos es del número conectado, y `radar_grupos` solo acumula.** `sincronizarGrupos` inserta los nuevos y actualiza los conocidos, pero **nunca borra**: al cambiar de número la tabla queda mezclada con los grupos del anterior. Por eso `supabase/radar-ia-grupos-vigencia.sql` agrega `visible`/`visto_en`: cada sincronización marca `visible=false` a los que el número actual ya no ve, y `/radar-ia > Grupos` los tacha — en rojo (*"Activo pero sin acceso"*) si además siguen en `activo`, que es el caso que engaña: aparentan vigilancia y no puede llegar un mensaje. **No se borran** (conservan el `contexto` para ELIA, las `categorias_permitidas` y los `radar_mensajes.grupo_id`); se quitan a mano. Dos reglas al tocar esto: una lista vacía de WhatsApp **no** marca nada (también es lo que devuelve una sesión a medio iniciar), y en el cliente la ausencia de la columna se trata como visible (`g.visible !== false`, nunca `!g.visible`) porque las filas anteriores al SQL no la traen. `detectarVigencia()` en `db.ts` sondea la columna una vez y degrada sin romper la sincronización si el SQL no se corrió. La lectura (`groupFetchAllParticipating`) va con **3 reintentos**: WhatsApp responde 408 con frecuencia justo después de vincular, y antes eso dejaba la lista intacta hasta el barrido de 30 min sin ninguna señal; `radar_estado.grupos_sincronizados_en` guarda solo las lecturas EXITOSAS, y `solicitar_sync_grupos` es el botón "Actualizar lista" (mismo patrón que `solicitar_relink`; ambas banderas se leen en una sola consulta con `leerSolicitudes`).

**Cambiar el número vinculado / que aparezca el QR.** La regla que explica todo el módulo de conexión: **Baileys solo emite el evento `qr` cuando `auth/` está vacío**. Mientras esa carpeta conserve credenciales, el worker reintenta con ellas para siempre y en `/radar-ia` no aparece ningún código. Por eso las credenciales inservibles se BORRAN en vez de reintentarse: `CODIGOS_SESION_MUERTA` en `radar-worker/src/index.ts` mapea 401 (desvinculado), **403 (WhatsApp bloqueó el número por usar un cliente no oficial — el riesgo real de Baileys)**, 405 y 411 a `forzarQrNuevo()`, que jubila el socket, borra `auth/` y reconecta. El 500 (`badSession`) **no** entra ahí: en Baileys es el default de cualquier error no mapeado y borrar la sesión por un error transitorio la destruiría. El botón "Generar QR nuevo" (`solicitar_relink`) llama al mismo `forzarQrNuevo()`: el `sock.logout()` previo es solo cortesía, best-effort y con tope de 5 s, porque **con el socket caído — justo cuando más falta hace el QR — nunca completa**. Los códigos van como literales (`COD`) y no vía el enum `DisconnectReason`, que depende de la interop CJS/ESM. Un contador de generación descarta los eventos de sockets jubilados, incluido el `creds.update` que si no volvería a escribir `auth/` recién borrado. `config.version` se publica en `radar_estado.version_worker` y `/radar-ia` la muestra: sirve para saber si el droplet quedó en una versión vieja (el botón necesita **1.1.0+**).

### Conventions

- `@/*` in `tsconfig.json` resolves to the repo root, so `@/lib/supabase` ≡ `lib/supabase.ts`.
- Almost every page is a Client Component (`"use client"`) that fetches Supabase directly. Server Components are rare; don't refactor a page to a Server Component without rechecking the auth/permission flow above.
- Date handling assumes Peru (UTC-5). Don't rely on `new Date().toISOString()` for "today" — see `getFechaLocal()` in `app/conductor/page.tsx` and the Lima offset math in `app/api/notificaciones/recordatorio/route.ts`.
- CSV/Excel parsing for paradas/manifiesto goes through `lib/paradas-csv.ts`, `lib/manifiesto-csv.ts`, and `lib/manifiesto-unificado-csv.ts` (uses `xlsx`).
- Maps: Mapbox GL for in-app rendering, Google Directions for routing — coordinate order is `[lng, lat]` end-to-end (Mapbox convention) once it leaves `/api/ruta`.
